Capítulo 1

A regra dos 80%: o dado antes do modelo

Todas as páginas anteriores partiram de um corpus pronto: 48 trechos com id, dispositivo e conteudo. Esse arquivo é a parte mais trabalhosa do sistema, e a que mais define a qualidade. Um trecho cortado no lugar errado vira uma citação impossível de conferir; um cabeçalho de página que sobrou vira "Presidência da República" dentro de um inciso; um hífen de quebra de linha que ficou vira uma palavra que a busca lexical nunca encontra ("automo-tores"). Nenhum modelo conserta isso depois. Por isso o Ex. 2 é o exercício de dados, e por isso ele é o mais longo.

O caminho do PDF ao banco tem sete estações, e cada uma tem um artefato que dá para abrir e olhar. Essa é a regra de trabalho da página: nunca passe para a próxima estação sem olhar o artefato da anterior. O texto bruto se lê num editor; o limpo se compara com o bruto; os dispositivos se contam; o JSONL se inspeciona com pandas; o modelo Pydantic rejeita linha por linha; o banco se consulta. O que não foi olhado está errado até prova em contrário.

Antes de qualquer código, vale olhar o texto bruto com atenção. O experimento abaixo mostra uma página da lei como o pymupdf a entrega, com os problemas marcados por categoria. Cada categoria tem uma regra de limpeza no capítulo 3; a categoria "marcadores" não é problema, é o que o segmentador do capítulo 5 vai procurar, e por isso precisa sobreviver intacta à limpeza.

Perguntas que aparecem aqui

    
Não dá para pular a limpeza e mandar o texto bruto para o modelo de embeddings?

Porque a citação precisa ser conferível: "Art. 75, I" é algo que o auditor abre e lê. "Trecho 37, tokens 18.500 a 19.000" não é. Capítulo 2
Extrair texto de PDF: o que há dentro e como tirar


  
Um PDF não guarda texto do jeito que um .txt guarda. Ele guarda instruções de desenho: "na posição (72, 540), com a fonte F1 em 11 pontos, desenhe os glifos 'Art. 75.'". Não existe o conceito de parágrafo, de coluna nem de ordem de leitura. O que a biblioteca de extração faz é reconstruir linhas a partir de glifos próximos, e blocos a partir de linhas próximas, e adivinhar a ordem. Por isso duas bibliotecas dão textos diferentes do mesmo arquivo, e por isso a ordem de leitura de uma página em duas colunas pode sair embaralhada.

  
Há ainda um segundo tipo de PDF: o escaneado. Nele não há glifos, só uma imagem por página; extrair texto significa reconhecer caracteres na imagem (OCR). A lei no Planalto é um PDF "nativo" (tem camada de texto); um contrato assinado e digitalizado que o sistema do projeto vai auditar frequentemente não é. O código precisa detectar qual é o caso por página e escolher o caminho.

Perguntas que aparecem aqui

    
Como sei se o PDF é nativo ou escaneado sem abrir?
Contando caracteres por página com o próprio pymupdf: len(page.get_text()). Nativo tem centenas a milhares por página; escaneado tem zero (ou lixo, se alguém já rodou um OCR ruim). Um segundo sinal: page.get_images() devolve uma imagem do tamanho da página. O detector do experimento faz exatamente isso. Não confie no nome do arquivo nem em quem mandou.
Decisão por página, com contagem, não por aparência.

    
Copiar do site do Planalto (HTML) não seria melhor que o PDF?
Para a lei, sim: o HTML tem a estrutura marcada e nenhuma hifenização, e é o que muita gente usa. O Ex. 2 escolhe o PDF de propósito, porque o sistema do projeto vai receber PDFs de contratos e editais, não HTML, e as habilidades (extrair, limpar, segmentar) são as mesmas. Depois de fechar o exercício com o PDF, comparar com o HTML é uma boa verificação: os ids têm de coincidir.
O PDF é o caso real; o HTML é uma verificação.

    
O que é o sort=True exatamente?
pymupdf ordena os blocos de texto pela coordenada vertical (y) e, em empate, pela horizontal (x), reconstruindo a ordem "de cima para baixo, da esquerda para a direita". Numa coluna só, é o certo. Em duas colunas, intercala as linhas das duas, porque compartilham o mesmo y. Para colunas, pegue os blocos com get_text("blocks"), agrupe por x0 (esquerda e direita) e ordene por y dentro de cada grupo.
sort=True resolve uma coluna; colunas exigem agrupar por x.

    
OCR em português precisa de algo especial?
Do pacote de idioma (tesseract-ocr-por) e de resolução: 300 dpi na renderização. Sem o idioma, o tesseract não reconhece acentos nem cedilha. Mesmo com tudo certo, espere 1 a 3% de caracteres errados em documentos limpos e bem mais em cópias de fax; por isso o resultado de OCR entra no sistema com a marca origem: "ocr" nos metadados, para a validação (página 7) ser mais desconfiada com esses trechos.
OCR é fonte de segunda categoria: marcada e revisada.

    
E tabelas? A lei não tem, mas contratos têm.
Tabela extraída como texto corrido vira uma sequência de células sem sentido. Para tabelas, pdfplumber com extract_tables(), e cada tabela vira um trecho próprio, com o conteúdo em formato de linhas "coluna: valor" ou Markdown, e o dispositivo do tipo "Anexo I, Tabela 2". É trabalho à parte, e o projeto o adia: primeiro o texto corrido.
Tabela é outro tipo de trecho, com outra ferramenta.

Capítulo 3
Limpeza: cabeçalhos, hifenização, quebras e o Unicode invisível


  
A limpeza é uma sequência de regras, e a ordem importa. Remover cabeçalho e rodapé precisa acontecer antes de juntar linhas, senão o rodapé é colado ao inciso anterior. Normalizar Unicode precisa vir antes da hifenização, porque o hífen de quebra às vezes é um hífen suave (U+00AD) que a regex de "-" não vê. Desfazer a hifenização precisa vir antes de juntar linhas, porque depois de juntas "automo- tores" ganha um espaço e o hífen já não está no fim de linha. Cada regra tem um risco de estragar algo, e a tabela diz qual.

    A segunda metade da limpeza é invisível. Um texto que parece igual pode ter dois "ç" diferentes: o caractere composto (U+00E7) e o "c" seguido de uma cedilha combinante (U+0327), que o PDF às vezes emite. Para a busca lexical são duas palavras distintas; para o hash de conteúdo do capítulo 9, dois trechos distintos. O mesmo vale para o espaço não separável (U+00A0), o hífen suave (U+00AD), a ligadura "ﬁ" (U+FB01) e o sinal de grau (°) usado no lugar do ordinal (º). A forma de normalização NFC compõe os caracteres (c + cedilha → ç); a NFKC faz isso e também troca as formas de compatibilidade (ligaduras, sobrescritos) pela forma simples. Para texto de lei, NFKC é a escolha, com o cuidado da tabela.

      Perguntas que aparecem aqui
      
    
      Como detectar cabeçalho e rodapé sem escrever uma regex para cada documento?
      Por repetição: cabeçalho e rodapé aparecem em quase todas as páginas, no mesmo lugar, com o mesmo texto (ou o mesmo texto a menos de um número de página). Divida o bruto por página, conte em quantas páginas cada linha aparece (com os dígitos substituídos por #), e remova as que aparecem em mais de 30% das páginas. Isso generaliza para qualquer documento; a regex do rodapé do Planalto é só um atalho para o caso conhecido.
      Repetição entre páginas é a assinatura de cabeçalho e rodapé.
      
    
      A regra 3 pode juntar palavras erradas?
      Pode, quando a palavra tem hífen legítimo e a quebra caiu nele: "contra-\nordem" viraria "contraordem". A condição "a linha seguinte começa com minúscula" evita a maioria dos casos de nomes próprios, mas não esse. Duas saídas: manter uma lista de palavras hifenizadas frequentes no domínio (decreto-lei, contra-ordem, ex-servidor) e não juntar quando o resultado for uma delas; ou aceitar a taxa de erro (rara) e registrar. O projeto aceita e registra.
      Regras têm taxa de erro; conheça-a e decida.
      
    
      Por que não usar o modelo de linguagem para limpar?
      Custo e determinismo. Limpar 120 páginas com o modelo custa tokens a cada rodada e produz resultados diferentes a cada vez, o que quebra o hash de conteúdo e a reprodutibilidade. Regras são grátis, instantâneas e dão o mesmo resultado sempre; e quando erram, erram de forma previsível, que se corrige uma vez. O modelo entra onde regra não alcança (capítulo 5 tem um experimento comparando os dois na segmentação).
      Regra é barata, determinística e corrigível; modelo não.
      
    
      NFC ou NFKC?
      NFC compõe (c + cedilha → ç) e é segura sempre. NFKC também substitui formas de compatibilidade: ligaduras ("ﬁ" → "fi"), sobrescritos ("²" → "2"), espaços especiais. Para texto normativo, o ganho das ligaduras vale mais que a perda dos raros sobrescritos; o projeto usa NFKC e trata "º" e "ª" à parte (NFKC transforma "º" em "o", o que destruiria "1º" → "1o": por isso a regra 2 protege os ordinais antes de normalizar e os restaura depois).
      NFKC, com proteção explícita dos ordinais.
      
    
      O texto limpo deve ter uma linha por dispositivo?
      É o alvo: depois da regra 4, cada linha começa com um marcador (Art., §, inciso, alínea) ou é continuação de uma frase que não coube. O segmentador do capítulo 5 assume isso. Se ao abrir o limpo você vir muitas linhas curtas sem marcador, a regra 4 não está juntando o que devia, e a causa costuma ser um marcador não reconhecido pela regex (que é a do capítulo 4).
      Linha = dispositivo é o contrato entre limpeza e segmentação.

      Capítulo 4
      Expressões regulares: a gramática da lei
      

  
      Uma lei brasileira tem uma gramática visual estável: Art. 75. abre um artigo; § 1º abre um parágrafo; I -, II - abrem incisos; a), b) abrem alíneas; e dentro de alíneas, raramente, 1., 2. abrem itens. Uma expressão regular é a forma de descrever essa gramática de modo que o código a reconheça no início de cada linha. O capítulo ensina a ler e escrever regex do zero, com os pedaços que o segmentador usa, e termina com a galeria das armadilhas: os casos em que a regex "óbvia" acerta 95% e erra justamente o Art. 1º, o Art. 10 e o Parágrafo único.
      

  
      
    
      PedaçoSignificaNo segmentador
      
    
      
      ^ e $Início e fim da linha (com a flag re.M); sem ela, início e fim do texto inteiro.^Art\. exige que o marcador esteja no começo da linha: "conforme o Art. 75" no meio de uma frase não abre artigo.
      
      
      \d+, \s*, \wUm ou mais dígitos; zero ou mais espaços; caractere de palavra (letras, dígitos, _; com acentos em Python 3).Art\.\s*(\d+) aceita "Art.75" e "Art. 75".
      
      
      [º°.]?Uma classe de caracteres: um destes; ? torna opcional."Art. 1º", "Art. 10." e "Art. 75" com o mesmo padrão.
      
      
      (?P<num>…)Grupo nomeado: captura a parte e dá um nome (m.group('num'), m['num']).Cada marcador captura o número no nome certo: art, par, inc, ali.
      
      
      A|BAlternância: A ou B. Com grupos nomeados, uma regex reconhece todos os marcadores e diz qual casou.^(?:(?P<art>Art\. …)|(?P<par>§ …)|(?P<inc>[IVXL]+ -)|(?P<ali>[a-z]\)))
      
      
      [IVXL]+ e (?=\s*[-–—])Classe de algarismos romanos; lookahead: exige que venha um traço depois, sem consumi-lo.Evita que "I" no começo de "Item" ou "V" em "Vedado" seja lido como inciso.
      
      
      re.M, re.I, re.XMultilinha (^ e $ por linha); ignorar maiúsculas; modo verboso (espaços e comentários dentro do padrão).re.M sempre; re.X para a regex grande dos marcadores caber em várias linhas comentadas.

      Perguntas que aparecem aqui
      
    
      Regex não é frágil demais para isso? E se a lei mudar o formato?
      O formato dos marcadores é a parte mais estável de uma norma brasileira: a Lei Complementar 95/1998 define como artigos, parágrafos, incisos e alíneas são escritos, e todas as leis federais desde então seguem. Contratos e editais são menos disciplinados, e aí a regex precisa de mais alternativas (CLÁUSULA PRIMEIRA, 1.1, 1.1.1). Frágil seria uma regex sem testes; com o teste do Art. 75 no capítulo 10, qualquer mudança que a quebre aparece na hora.
      A gramática é normatizada; a fragilidade se cobre com testes.
      
    
      Por que grupos nomeados em vez de numerados?
      Porque a regex dos marcadores é longa e muda. Com grupos numerados, inserir uma alternativa no meio renumera todas as seguintes e quebra o código que lê m.group(3). Com nomes, m['inc'] continua valendo. E m.lastgroup diz qual alternativa casou, que é exatamente o que a máquina de estados do capítulo 5 precisa saber.
      Nomes sobrevivem a edições; números não.
      
    
      Qual a diferença entre match, search e fullmatch?
      match só casa no início da string; search acha em qualquer posição; fullmatch exige que a string inteira case. O segmentador usa match por linha (o marcador tem de estar no começo). A limpeza usa sub, que internamente é um search repetido. Usar search no segmentador é o erro clássico: "conforme o Art. 75" no meio de um inciso abriria um artigo.
      match no início da linha é o que impede falsos marcadores.
      
    
      O laboratório usa JavaScript; o Python vai se comportar igual?
      Para os pedaços desta página, sim: âncoras, classes, quantificadores, grupos nomeados (o laboratório converte (?P<n> para a forma do JavaScript) e lookahead são iguais. Diferenças que importam: no Python, \w inclui letras acentuadas por padrão; no JavaScript, só com a flag u e \p{L}. O laboratório já usa a flag u. E a flag re.X (verbosa) não existe no JavaScript; o capítulo 10 usa re.X no código Python para comentar a regex grande.
      Mesma sintaxe no essencial; \w e re.X são as diferenças.
      
    
      Preciso decorar tudo isso?
      Não. Precisa saber ler uma regex pedaço por pedaço e testar cada pedaço num laboratório como este (ou no regex101.com com o sabor Python) antes de colocar no código. E precisa da disciplina de nunca mudar a regex sem rodar o teste do Art. 75.
      Ler, testar por pedaço, e um teste que trava o comportamento.

      Capítulo 5
      O segmentador: máquina de estados e identificador natural
      

  
      Reconhecer marcadores não basta: o segmentador precisa saber onde está na hierarquia para dar o identificador certo. O inciso "I" depois de "Art. 75." é art75-incI; o mesmo "I" depois de "§ 1º" é art75-p1-incI. A forma mais simples e robusta de guardar esse "onde estou" é uma máquina de estados com uma pilha: o estado é (artigo, parágrafo, inciso, alínea) e cada marcador altera o estado a partir do seu nível para baixo. Um novo artigo zera tudo; um parágrafo zera inciso e alínea; um inciso zera a alínea; uma alínea só se coloca. Linha sem marcador é continuação: vai para o conteúdo do último trecho emitido.
      
  
      O identificador é montado a partir do estado, e é por isso que ele é natural: não depende da ordem de processamento nem de um contador. Reprocessar a lei de novo, com outra regex ou daqui a um ano, produz os mesmos ids para os mesmos dispositivos. É essa propriedade que permite o ON CONFLICT (id) do capítulo 9 e a citação estável das páginas 5 e 7.

        Perguntas que aparecem aqui
        
    
        Por que uma pilha e não uma árvore?
        Porque a lei é lida em sequência e cada marcador só depende do estado corrente. A pilha (ou simplesmente quatro variáveis) é tudo o que a sequência precisa. A árvore aparece como resultado (o experimento a desenha), mas o algoritmo não precisa construí-la para emitir os trechos. Menos estrutura, menos lugares para errar.
        Leitura sequencial pede estado, não árvore.
        
    
        O que fazer com "Parágrafo único"?
        É um parágrafo sem número: o estado recebe par = 'u' e o id vira art74-pu. Quando a lei é alterada e o parágrafo único ganha irmãos, ele passa a ser "§ 1º" no texto consolidado; o id muda e é correto que mude, porque o dispositivo mudou de nome. O mapeamento antigo→novo fica registrado nos metadados de vigência (página 5).
        pu é um estado como qualquer outro; a renumeração é um evento de vigência.
        
    
        E "Art. 75-A", "§ 1º-A", incisos "I-A"?
        São dispositivos inseridos por alteração posterior sem renumerar os vizinhos. A regex captura o sufixo ((?P<art>\d+)(?P<sufixo>-[A-Z])?) e o id o incorpora: art75A, p1A, incIA. A v3 do experimento faz isso. A ordem de leitura (75, 75-A, 76) é a do texto, e o id não tenta representar ordem: é nome, não posição.
        Sufixos entram no id; o id é nome, não posição.
        
    
        O texto do caput deve entrar no conteúdo dos incisos?
        Como prefixo, sim, e a página 5 explicou por quê: o inciso sozinho ("para contratação que envolva valores inferiores a…") não diz do que se trata. O segmentador emite o inciso com o conteúdo "É dispensável a licitação: para contratação que…" (caput até os dois-pontos + inciso), e guarda também o texto puro do inciso num campo texto_proprio. A busca usa o conteúdo com prefixo; a citação literal usa o texto próprio.
        Prefixo para busca; texto próprio para citar.
        
    
        O modelo acertou quase tudo no experimento ao vivo. Por que não usar ele?
        Rode duas vezes e compare: é comum a lista mudar entre execuções, e é comum aparecer um inciso que não existe ou faltar uma alínea. "Quase tudo" numa lei de 194 artigos são dezenas de dispositivos errados, sem nenhuma forma de saber quais. A regex acerta 100% dos casos que ela conhece e falha de forma visível nos que não conhece, e o teste do Art. 75 pega. Para estrutura, determinismo vale mais que inteligência.
        Estrutura pede determinismo; o modelo entra onde não há estrutura.

        Capítulo 6
        JSONL: o formato de trabalho
        

  
        JSON Lines é um arquivo de texto com um objeto JSON por linha, sem colchetes em volta e sem vírgula entre as linhas. É o formato de trabalho do projeto para trechos, casos de avaliação (página 8) e registros de execução (página 5), pelas mesmas razões: pode ser lido linha a linha sem carregar tudo na memória; pode ser acrescentado no fim (append) sem reescrever; uma linha corrompida não invalida o arquivo; wc -l conta registros; grep art75 acha um; e o git diff mostra exatamente quais registros mudaram. Um JSON com um array faz o oposto em cada um desses pontos.

        Perguntas que aparecem aqui
        
    
        Por que não gravar direto no banco e pular o JSONL?
        Porque o JSONL é o artefato que se olha, se versiona e se compara entre execuções. O banco é o destino, e é reconstruível a partir do JSONL a qualquer momento (carregar.py); o contrário não é tão simples. Ter o arquivo no git significa que uma mudança na regex aparece como diff de trechos, revisável antes de tocar no banco.
        JSONL é o artefato revisável; o banco é derivado dele.
        
    
        Um trecho por linha não deixa a linha enorme?
        Deixa, e não importa: nenhuma ferramenta que lê JSONL se incomoda com linhas de 5.000 caracteres. O que importa é que a quebra de linha real dentro do conteúdo vire \n escapado, coisa que json.dumps faz sozinho. Para ler com os olhos, jq -c '.id, (.conteudo | .[0:80])' trechos.jsonl ou o pandas do capítulo 7.
        Linha longa é normal; o que não pode é quebra de linha crua.
        
    
        Como versionar o arquivo quando a lei muda?
        O arquivo é data/trechos.jsonl e o git guarda a história. Quando uma alteração legal entra, os trechos afetados mudam de conteúdo (e ganham vigencia_fim os revogados); o diff mostra exatamente quais. O hash do conteúdo, gravado por linha, é o que o capítulo 9 usa para não reembutir o que não mudou.
        git para a história; hash por linha para o incremental.
        
    
        Os metadados (vigência, origem, hash) vão na mesma linha?
        Sim: cada linha tem tudo o que o trecho precisa: id, dispositivo, conteudo, texto_proprio, artigo, tipo, vigencia_inicio, vigencia_fim, origem, hash. É o modelo Pydantic do capítulo 8. O que não vai na linha é o embedding: 768 números por trecho triplicariam o arquivo e mudariam sempre que o modelo de embedding mudasse. Embedding mora no banco.
        Metadados na linha; embedding no banco.

        Capítulo 8
        Pydantic: o contrato dos dados
        

  
        pandas mostra o que está errado; Pydantic impede que o errado passe. Um modelo Pydantic é uma classe que declara os campos, os tipos e as regras de um registro; Trecho.model_validate(obj) devolve um objeto tipado se o registro obedece ao contrato, ou levanta ValidationError com uma lista de erros, cada um com o campo (loc), a mensagem (msg) e um código (type). O mesmo mecanismo que a página 6 usou para a resposta do modelo de linguagem (esquema de saída) vale para o dado de entrada: o contrato fica num lugar só, em código, e é ele que o segmentador, o carregador e a API respeitam.

        O modelo Trecho à esquerda; um registro à direita. Edite ou escolha um caso e valide: os erros saem como o Pydantic os imprime, e a linha do modelo responsável acende.
        
      
        
      
        
        
        class Trecho(BaseModel):
    model_config = ConfigDict(extra='forbid', str_strip_whitespace=True)
    id: str = Field(pattern=r'^L\d+-art\d+[A-Z]?(-p(\d+[A-Z]?|u))?(-inc[IVXL]+[A-Z]?)?(-[a-z])?$')
    dispositivo: str = Field(min_length=3)
    conteudo: str = Field(min_length=20)
    artigo: int = Field(ge=1)
    tipo: Literal['caput', 'paragrafo', 'inciso', 'alinea']
    vigencia_inicio: date
    vigencia_fim: date | None = None

    @field_validator('conteudo')
    @classmethod
    def sem_marcador(cls, v: str) -> str:
        if re.match(r'^(Art\.|§|[IVXL]+\s*-|[a-z]\))', v):
            raise ValueError('conteúdo começa com marcador: segmentação incompleta')
        return v

    @model_validator(mode='after')
    def coerente(self):
        if self.vigencia_fim and self.vigencia_fim < self.vigencia_inicio:
            raise ValueError('vigencia_fim anterior a vigencia_inicio')
        if int(re.search(r'art(\d+)', self.id).group(1)) != self.artigo:
            raise ValueError('artigo não bate com o id')
        return self

        Perguntas que aparecem aqui
        
    
        Pydantic ou dataclass ou TypedDict?
        dataclass e TypedDict declaram a forma mas não validam: um Trecho(artigo="abc") é aceito. Pydantic valida na construção e dá mensagens por campo. Para dados que vêm de fora (arquivo, API, modelo de linguagem), validar é o ponto; para estruturas internas que o próprio código cria, dataclass basta e é mais leve.
        Dado que cruza uma fronteira é validado; dado interno pode ser dataclass.
        
    
        Onde o modelo Trecho é usado além da carga?
        Em quatro lugares: o segmentador constrói Trecho(...) antes de gravar (erro aparece na origem); o carregador valida cada linha do JSONL antes do INSERT; a API do sistema devolve trechos como Trecho.model_dump(); e o model_json_schema() documenta o formato. Um contrato, quatro usos, zero cópias divergentes.

        Capítulo 9
        psycopg: carregar sem duplicar e sem reembutir
        

  
        A carga é o último passo e o que mais custa quando feito errado: cada trecho embutido custa uma chamada de embedding, e reembutir a lei inteira porque um artigo mudou é jogar dinheiro e tempo fora. Três ideias resolvem: parâmetros em vez de montar SQL com texto (segurança e tipos corretos), transação por arquivo (ou tudo entra, ou nada), e upsert por chave natural com hash de conteúdo: INSERT … ON CONFLICT (id) DO UPDATE, e o embedding só é recalculado quando o hash do conteúdo mudou.

        Perguntas que aparecem aqui
        
    
        psycopg 2 ou 3?
        3 (pip install "psycopg[binary]"): API moderna, async se precisar, conn.transaction(), cur.copy(), e é o que o pgvector documenta (pgvector.psycopg). psycopg2 ainda é comum em código antigo e em tutoriais; a sintaxe de parâmetros (%s) é a mesma, o resto difere.
        psycopg 3 com pgvector.psycopg.
        
    
        Por que %s e não f-string, se eu confio nos meus dados?
        Dois motivos além da segurança. Tipos: com parâmetros, o driver envia datas, listas e vetores no formato que o servidor espera; com f-string, você mesmo formata e erra. E aspas: qualquer conteúdo com ' (a lei tem dezenas) quebra a string montada. O experimento mostra os três casos. A regra é absoluta no projeto: SQL nunca é montado com valores dentro; nomes de tabela e coluna, quando dinâmicos, usam psycopg.sql.Identifier.
        Parâmetros por tipos, aspas e segurança: sem exceção.
        
    
        executemany ou COPY?
        Para até alguns milhares de linhas, executemany com o upsert é simples e suficiente (psycopg 3 agrupa em pipeline). Para dezenas de milhares, COPY para uma tabela temporária e um único INSERT … SELECT … ON CONFLICT é dez a cinquenta vezes mais rápido. O código do capítulo 10 usa executemany, com a nota de onde trocar.
        executemany até milhares; COPY + tabela temporária acima.
        
    
        O que acontece com um trecho que sumiu do arquivo?
        Nada automático. Sumir do JSONL pode ser revogação (vigência encerrada), erro de regex nesta rodada ou renumeração. Apagar destruiria citações de pareceres antigos. O carregador lista os ids ausentes e um humano decide: vigencia_fim (página 5) ou correção da regex. O banco só apaga o que alguém mandou apagar.
        Ausência é sinal para revisão, não ordem de exclusão.
        
    
        Preciso de pool de conexões?
        Para o script de carga, não: uma conexão, uma transação. Para a API do sistema (várias consultas simultâneas), sim: psycopg_pool.ConnectionPool, com min_size e max_size pequenos (2 a 10). Abrir uma conexão por consulta custa dezenas de milissegundos e esgota o servidor.
        Script: uma conexão; serviço: pool.

def extrair(pdf: Path, txt: Path) -> str:

def ocr(page) -> str:

    from PIL import Image
    pix = page.get_pixmap(dpi=300)
    img = Image.frombytes("RGB", (pix.width, pix.height), pix.samples)

# ---------- marcadores (capítulo 4) ----------
MARCADOR = re.compile(r"""^(?:
    (?P<art>Art\.\s*(?P<art_n>\d+)(?P<art_s>-[A-Z])?\s*[º°.]?)                 # Art. 75.  Art. 1º  Art. 75-A.
  | (?P<par>§\s*(?P<par_n>\d+)\s*[º°]?(?P<par_s>-[A-Z])?|Parágrafo\s+único\.?)  # § 1º  § 1º-A  Parágrafo único
  | (?P<inc>(?P<inc_n>[IVXL]+)(?P<inc_s>-[A-Z])?\s*[-–—])                        # I -  IV-A -
  | (?P<ali>(?P<ali_n>[a-z])\))                                                # a)
)\s*""", re.X)
RODAPE = re.compile(r"planalto\.gov\.br|^\s*\d+\s*/\s*\d+\s*$")

# ---------- 2. limpar (capítulo 3: a ordem importa) ----------
def limpar(bruto: str) -> str:
    paginas = bruto.split("\f")
    # regra 1: linhas repetidas em >= 30% das páginas (dígitos → #) são cabeçalho/rodapé
    assinatura = lambda l: re.sub(r"\d", "#", l.strip())
    freq = Counter(assinatura(l) for p in paginas for l in set(p.splitlines()) if l.strip())
    limiar = max(3, int(0.3 * len(paginas)))
    repetidas = {a for a, n in freq.items() if n >= limiar and len(a) < 80}
    linhas = [l for p in paginas for l in p.splitlines() if l.strip()
              and not RODAPE.search(l)
              and not (assinatura(l) in repetidas and not MARCADOR.match(l))]
    s = "\n".join(linhas)
    # regra 2: Unicode (protege os ordinais: NFKC transformaria º em o)
    s = s.replace("º", "\x00o").replace("ª", "\x00a")
    s = unicodedata.normalize("NFKC", s)
    s = s.replace("\x00o", "º").replace("\x00a", "ª")
    s = s.replace("\u00a0", " ").replace("\u00ad", "").replace("\u200b", "")   # nbsp, hífen suave, largura zero
    s = re.sub(r"(\d)°", r"\1º", s)                                   # grau → ordinal
    s = re.sub(r"^([IVXL]+(?:-[A-Z])?)\s*[–—]", r"\1 -", s, flags=re.M)  # travessão → hífen no inciso
    # regra 3: hifenização de fim de linha (só quando a próxima começa com minúscula)
    s = re.sub(r"(\w)-\n([a-zà-ú])", r"\1\2", s)
    # regras 4 e 5: juntar linhas quebradas; normalizar espaços
    out: list[str] = []
    for l in s.split("\n"):
        l = re.sub(r"[ \t]+", " ", l).strip()
        if out and not re.search(r"[.;:]$", out[-1]) and not MARCADOR.match(l):
            out[-1] += " " + l                 # continuação de frase
        else:
            out.append(l)
    return "\n".join(out)

# ---------- 3. segmentar (capítulo 5: máquina de estados) ----------
def montar_id(e: dict) -> str:
    partes = [LEI, f"art{e['art']}"]
    if e["par"]: partes.append(f"p{e['par']}")
    if e["inc"]: partes.append(f"inc{e['inc']}")
    if e["ali"]: partes.append(e["ali"])
    return "-".join(partes)

def segmentar(limpo: str) -> list[dict]:
    trechos, por_id = [], {}
    e = {"art": None, "par": None, "inc": None, "ali": None}
    sufixo = lambda s: (s or "").replace("-", "")
    for linha in limpo.split("\n"):
        m = MARCADOR.match(linha)
        if not m:
            if trechos: trechos[-1]["texto_proprio"] += " " + linha   # continuação
            continue
        texto = linha[m.end():].strip()
        tipo = next(k for k in ("art", "par", "inc", "ali") if m.group(k))
        if tipo == "art":
            e.update(art=m["art_n"] + sufixo(m["art_s"]), par=None, inc=None, ali=None)
            disp, tipo_t = f"Art. {m['art_n']}{m['art_s'] or ''}, caput", "caput"
        elif tipo == "par":
            n = "u" if m["par_n"] is None else m["par_n"] + sufixo(m["par_s"])
            e.update(par=n, inc=None, ali=None)
            disp, tipo_t = f"Art. {e['art']}, " + ("parágrafo único" if n == "u" else f"§ {n}º"), "paragrafo"
        elif tipo == "inc":
            e.update(inc=m["inc_n"] + sufixo(m["inc_s"]), ali=None)
            pai = ("parágrafo único, " if e["par"] == "u" else f"§ {e['par']}º, ") if e["par"] else ""
            disp, tipo_t = f"Art. {e['art']}, {pai}{e['inc']}", "inciso"
        else:
            e["ali"] = m["ali_n"]
            disp, tipo_t = f"Art. {e['art']}, {e['inc']}, {e['ali']}", "alinea"
        if e["art"] is None:
            continue                                  # marcador antes do primeiro artigo: preâmbulo
        # só inciso e alínea herdam prefixo: do caput/parágrafo e do inciso, respectivamente
        pai_id = montar_id({**e, "ali": None}) if tipo == "ali" else \
                 montar_id({**e, "inc": None, "ali": None}) if tipo == "inc" else None
        t = {"id": montar_id(e), "dispositivo": disp, "tipo": tipo_t, "texto_proprio": texto,
             "artigo": int(re.match(r"\d+", e["art"]).group()), "pai_id": pai_id,
             "vigencia_inicio": VIGENCIA, "origem": "pdf"}
        trechos.append(t); por_id[t["id"]] = t
    # conteúdo = conteúdo do pai (se o texto dele termina em ':') + texto próprio (página 5);
    # os pais vêm antes na lista, então o prefixo da alínea já inclui o do inciso
    for t in trechos:
        pai = por_id.get(t.pop("pai_id") or "")
        prefixo = pai["conteudo"] + " " if pai and pai["texto_proprio"].endswith(":") else ""
        t["conteudo"] = (prefixo + t["texto_proprio"]).strip()
        t["hash"] = hashlib.sha256(t["conteudo"].encode()).hexdigest()
    return trechos

import re
from datetime import date
from typing import Literal
from pydantic import BaseModel, ConfigDict, Field, field_validator, model_validator

class Trecho(BaseModel):
    model_config = ConfigDict(extra="forbid", str_strip_whitespace=True)
    id: str = Field(pattern=r"^L\d+-art\d+[A-Z]?(-p(\d+[A-Z]?|u))?(-inc[IVXL]+[A-Z]?)?(-[a-z])?$")
    dispositivo: str = Field(min_length=3)
    conteudo: str = Field(min_length=20)
    texto_proprio: str = Field(min_length=1)
    artigo: int = Field(ge=1)
    tipo: Literal["caput", "paragrafo", "inciso", "alinea"]
    vigencia_inicio: date
    vigencia_fim: date | None = None
    origem: Literal["pdf", "ocr", "html"] = "pdf"
    hash: str = Field(pattern=r"^[0-9a-f]{64}$")

    @field_validator("conteudo", "texto_proprio")
    @classmethod
    def sem_marcador(cls, v: str) -> str:
        if re.match(r"^(Art\.|§|[IVXL]+\s*-|[a-z]\))", v):
            raise ValueError("conteúdo começa com marcador: segmentação incompleta")
        return v

    @model_validator(mode="after")
    def coerente(self):
        if self.vigencia_fim and self.vigencia_fim < self.vigencia_inicio:
            raise ValueError("vigencia_fim anterior a vigencia_inicio")
        if int(re.search(r"art(\d+)", self.id).group(1)) != self.artigo:
            raise ValueError("artigo não bate com o id")
        return self
