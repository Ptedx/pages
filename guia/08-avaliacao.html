Página 8 · Medição

Avaliação

Todas as páginas anteriores terminaram na mesma frase: "meça no conjunto de avaliação". Esta página constrói esse instrumento. O que é um caso e como se fabrica um que meça alguma coisa; as métricas de busca (recall@k, MRR, nDCG) e as de resposta (fidelidade, cobertura, recusa correta); o protocolo que impede você de se enganar; a rodada completa do Ex. 7 aqui no navegador; e o que os números dizem quando n é pequeno, quando duas versões diferem por dois pontos, e quando o índice de conformidade precisa ser defendido diante de um auditor.

Ao terminar esta página você consegue

  • Dizer o que cada um dos quatro alvos do projeto (recall@k ≥ 0,80, fidelidade ≥ 0,98, cobertura ≥ 0,70, recusa correta ≥ 0,90) mede, e o que significa cada um ficar abaixo.
  • Escrever um caso de avaliação bem formado, reconhecer um caso "vazado" e montar um conjunto com perguntas com resposta, sem resposta, casos-limite e injeções.
  • Calcular recall@k, precisão@k, MRR e nDCG à mão sobre um ranking, e explicar quando cada um muda.
  • Definir fidelidade, cobertura e recusa correta de forma operacional e medir a concordância de um juiz automático com rótulos humanos (kappa).
  • Seguir o protocolo (dev e teste separados, temperatura 0, três execuções, versões registradas) e reconhecer sobreajuste ao conjunto.
  • Ler um resultado com intervalo de confiança, comparar duas versões pareadas e defender o índice de conformidade com um número de concordância.
Capítulo 1

O que "bom" significa: quatro números e um contrato

Sem medição, a qualidade de um RAG é uma impressão: "parece bom nas perguntas que eu testei". Com medição, é um contrato: quatro números, cada um com um alvo, medidos num conjunto fixo, registrados por versão. O projeto fixou os seus: recall@k ≥ 0,80 (a busca entrega o trecho certo entre os k na maioria das perguntas), fidelidade ≥ 0,98 (o que o sistema afirma é sustentado pelo que cita), cobertura ≥ 0,70 (dos achados que auditores apontariam, o sistema aponta a maioria) e recusa correta ≥ 0,90 (quando a base não responde, o sistema diz que não responde). Os quatro medem partes diferentes, e é por isso que são quatro.

Repare na assimetria dos alvos. Fidelidade em 0,98 e cobertura em 0,70 dizem uma coisa sobre o projeto: é aceitável deixar passar; não é aceitável afirmar o que a fonte não diz. Um sistema de auditoria que aponta 70% dos achados com 98% de fidelidade é útil e confiável; um que aponta 95% com 90% de fidelidade faz o auditor conferir tudo, e perde a razão de existir. Os alvos codificam prioridades, e mudá-los é uma decisão de produto, não de engenharia.

Experimento · Painel-alvo

roda no navegador

Mova cada número e leia o que ele significa para o sistema quando fica abaixo do alvo. É o painel que a versão precisa passar para entrar.

faça agora

Coloque recall em 60% e os outros três no máximo. Leia: com o trecho certo chegando em 60% das perguntas, a fidelidade de 100% é "fiel ao que recebeu", e a cobertura não tem como passar de 60%. Agora recall em 95% e fidelidade em 90%: o sistema vê tudo e afirma coisas que a fonte não diz. Qual dos dois cenários você preferiria auditar? O projeto escolheu.

Perguntas que aparecem aqui

Por que não uma nota única de 0 a 10?

Porque uma nota única esconde qual parte falhou. Recall baixo com fidelidade alta pede mexer na busca; o contrário pede mexer no prompt ou na validação. Uma nota que soma as duas não diz nada sobre o que fazer. Quatro números com alvos são um diagnóstico; uma nota é uma opinião.

Métrica por componente aponta onde mexer.

De onde saíram os alvos 0,80 / 0,98 / 0,70 / 0,90?

De uma conversa de produto: o que o auditor tolera (deixar passar 30% dos achados numa primeira versão) e o que não tolera (uma afirmação errada em cada dez). São ponto de partida, revisados a cada ciclo com o cliente; o que não muda é que existem, estão escritos e são medidos antes de cada versão entrar.

Alvos são decisão de produto, registrada e revisável.

Fidelidade 0,98 é realista?

Com esquema de saída, evidência literal, validação em código e recusa bem calibrada, sim: a maioria das falhas de fidelidade é pega antes de virar resposta aceita, e a fidelidade se mede sobre as aceitas. É um alvo exigente de propósito, porque uma afirmação não sustentada em auditoria custa mais que uma recusa.

As camadas da página 7 existem para tornar 0,98 possível.

E a latência e o custo, não são métricas?

São, e a página 10 as trata como restrições: a versão precisa atender aos quatro alvos dentro de um orçamento de tempo e de tokens por documento. Qualidade sem orçamento é um protótipo.

Qualidade é o alvo; custo e tempo são as restrições.

Escreva os quatro alvos, o que cada um mede, e explique a assimetria (fidelidade 0,98 contra cobertura 0,70) com as suas palavras.

Capítulo 2

O conjunto de avaliação: fabricar casos que medem

Um caso é uma pergunta com o que se espera dela: os ids dos trechos que a respondem (esperado), uma resposta de referência revisada por uma pessoa, e o tipo. Quatro tipos, cada um medindo uma coisa: com resposta (mede recall, fidelidade, cobertura), sem resposta na base (mede recusa correta; a pergunta é plausível, mas a resposta está em outra norma), caso-limite (percentual na fronteira, vigência antiga, redação ambígua; mede estabilidade e ALERTA) e injeção (documento que tenta dar ordens; mede as camadas da página 6). Um conjunto só de perguntas fáceis com resposta mede uma coisa só e superestima tudo.

De onde vêm os casos, por ordem de valor: perguntas reais de analistas (anonimizadas), critérios de auditoria com excertos reais classificados por auditores, erros de produção (o laço de volta da página 7), e por último, casos escritos pela equipe. O que torna um caso ruim: a pergunta copia as palavras do trecho (a busca lexical acha sem esforço; o caso não mede nada; é o vazamento lexical), o esperado está errado (mede o erro, não o sistema), ou a pergunta é absurda (mede nada). O construtor abaixo aponta o vazamento pela sobreposição de radicais entre pergunta e trecho.

Tamanho e organização: dezenas de casos por critério, centenas no total, com os quatro tipos representados. Divididos em desenvolvimento (para iterar prompts e parâmetros) e teste (para o número final, tocado só quando uma versão candidata está pronta). Versionados como o corpus: avaliacao/v3.jsonl, com quem revisou cada caso. O capítulo 5 explica por que a divisão não é burocracia.

Perguntas que aparecem aqui

Posso gerar casos com o próprio modelo de linguagem?

Como rascunho, sim: "escreva dez perguntas que este trecho responde" produz candidatos rápido. Mas eles vêm com vazamento (o modelo reusa as palavras do trecho) e sem garantia de que o esperado está certo. Cada um precisa de reescrita e revisão humana antes de contar. Casos gerados e não revisados medem o gerador, não o sistema.

Gerado é rascunho; revisado é caso.

Quantos casos "sem resposta" o conjunto precisa?

Uma fração relevante, uns 20 a 30%, e plausíveis: perguntas do domínio cuja resposta está em outra norma (tributária, trabalhista) ou em dados que a base não tem. Perguntas absurdas medem nada. Sem casos assim, a recusa correta não é medida, e um sistema que nunca recusa passa com nota máxima.

Sem "sem resposta", a invenção é invisível.

O esperado pode ter mais de um id?

Pode e deve, quando a resposta está em mais de um dispositivo (o limite de obras e o de compras; o caput e o parágrafo). Recall conta acerto se qualquer esperado aparece entre os k; cobertura, na auditoria, conta quantos dos esperados foram apontados. O construtor do guia grava um id por caso para simplificar; no projeto, o campo é lista.

Lista de ids: recall por qualquer um, cobertura por todos.

Sobreposição lexical baixa garante um caso bom?

Não: garante que a lexical não acha de graça. O caso ainda pode estar com o esperado errado, ou a pergunta pode ser ambígua (duas respostas válidas). Sobreposição é um filtro barato para o erro mais comum; a revisão humana continua sendo o filtro que vale.

Filtro automático para o comum; pessoa para o resto.

Como manter o conjunto vivo?

Três entradas: erros de produção (com a saída esperada revisada), perguntas novas dos analistas a cada ciclo, e casos que a mudança de base torna necessários (uma norma nova, uma vigência que fechou). E uma saída: casos que ficaram triviais (todo mundo acerta há meses) podem ir para um conjunto de regressão rápida, liberando a leitura para os difíceis.

Entra o que o sistema errou; sai o que ninguém erra mais.

Descreva os quatro tipos de caso, as fontes por ordem de valor, o que é vazamento lexical e por que dev e teste são separados.

Capítulo 3

Métricas de busca: recall@k, precisão, MRR, nDCG

A busca devolve uma lista ordenada; o caso diz quais itens são relevantes. Todas as métricas de busca são formas de perguntar "os relevantes estão na lista, e onde?". Cada uma responde a uma parte.

MétricaPergunta que respondeFórmulaQuando usarCega para
recall@kdos relevantes, quantos estão entre os k?relevantes nos k ÷ relevantes totaisa métrica principal do projeto: o modelo vai ler os ka ordem dentro dos k; o lixo entre os k
precisão@kdos k, quantos são relevantes?relevantes nos k ÷ kquando cada item custa (tokens no prompt)relevantes que ficaram fora
hit@ktem pelo menos um relevante entre os k?1 ou 0 por pergunta, média no conjuntoperguntas com um único trecho esperado (vira recall@k)quantos relevantes; a ordem
MRRo primeiro relevante está em que posição?média de 1 ÷ posição do primeiro relevantequando só o topo importa (reranker, k pequeno)os relevantes depois do primeiro
nDCG@kos mais relevantes estão mais no topo?ganho com desconto logarítmico por posição ÷ ganho idealrelevância graduada (responde / relacionado); comparar rerankersdifícil de explicar a quem não é de busca

O projeto reporta recall@12 como alvo (o modelo lê os 12; o que importa é o certo estar lá) e MRR como diagnóstico (se o certo costuma estar em 9º, um reranker ou um k menor mudam as coisas). nDCG entra quando se compara rerankers, porque distingue "responde" de "só relacionado". Precisão@k quase não é usada: com trechos curtos, 12 itens cabem no orçamento, e o custo do lixo é pequeno.

Experimento · Calculadora de ranking

roda no navegador

Dez posições de um ranking. Clique num item para mudar a relevância (irrelevante → relacionado → responde). Mova o k. Todas as métricas recalculam; veja quais mudam e quais ficam iguais.

faça agora

Com a configuração inicial (relevantes em 2º, 4º, 7º e 10º), coloque k = 3: recall@3 baixo, MRR alto (o primeiro relevante está em 2º). Torne o 1º item "responde": MRR vai a 1 e nDCG sobe; recall@3 sobe um degrau. Agora mova k para 10: recall vira 100% e precisão cai. Cada métrica olha para um pedaço do mesmo ranking.

Perguntas que aparecem aqui

Por que o desconto do nDCG é logarítmico?

Porque a atenção de quem lê (ou do modelo, pelo efeito "perdido no meio") cai rápido nas primeiras posições e devagar depois: a diferença entre 1º e 2º importa mais que entre 9º e 10º. O logaritmo da posição modela isso; o ganho de um item na posição p vale (2^relevância − 1) ÷ log₂(p + 1). Normalizar pelo ranking ideal deixa o número entre 0 e 1 e comparável entre perguntas.

Desconto logarítmico: o topo pesa muito, a cauda pouco.

Recall@k sobe sempre com k; então k grande é melhor?

Recall sim; o sistema não: k grande enche o prompt com trechos irrelevantes (custo, e o modelo pode usar o errado). O k certo é o menor em que o recall estabiliza; a curva recall × k, que o Ex. 7 traça, mostra onde. No projeto ficou em 12 com folga; o número se revisa com o conjunto.

O k certo é onde a curva de recall achata.

MRR de 0,5 significa que o certo está em 2º?

Em média, sim, mas a média de recíprocos engana: metade das perguntas com o certo em 1º e metade sem o certo em lugar nenhum também dá 0,5. Leia MRR junto com recall e, quando puder, com a distribuição das posições (o experimento do capítulo 6 mostra a posição por pergunta).

Média de recíprocos: olhe a distribuição.

Como medir a busca quando o esperado tem vários ids?

Recall@k conta os esperados encontrados sobre o total de esperados (a fórmula da tabela); hit@k conta se algum apareceu. Para a auditoria, onde cada critério tem os seus dispositivos, recall por todos é o que interessa: o modelo precisa de todos para classificar.

Vários esperados: recall por fração, não por "algum".

Para cada métrica da tabela, escreva a pergunta que ela responde e uma situação em que ela muda enquanto as outras ficam iguais.

Capítulo 4

Métricas de resposta: fidelidade, cobertura, recusa, e quem rotula

Medir a busca é comparar listas: exato e barato. Medir a resposta é decidir se um texto é sustentado por outro, e isso exige uma definição operacional e alguém (ou algo) que aplique a definição igual em todos os casos. As três métricas do projeto são definidas assim:

MétricaDefinição operacionalQuem decideDenominador
fidelidadea resposta aceita cita o trecho esperado e não afirma nada que os trechos citados não sustentemcódigo (cita o esperado?) + juiz ou pessoa (afirmações sustentadas?)respostas aceitas pela validação
coberturados achados esperados de um documento (a lista dos auditores), quantos o sistema classificou como NAO_CONFORME ou ALERTA no critério certocódigo, contra a lista revisadaachados esperados
recusa corretaem pergunta sem resposta na base, o sistema devolveu sem_evidenciacódigoperguntas sem resposta
recusa indevidaem pergunta com resposta, o sistema devolveu sem_evidenciacódigoperguntas com resposta
exatidão (opcional)a resposta diz o mesmo que a referênciajuiz ou pessoaperguntas com referência

A parte que exige leitura ("afirmações sustentadas?", "diz o mesmo que a referência?") tem dois caminhos: pessoas, que são a referência mas não escalam, e um juiz automático (página 7), que escala mas precisa provar que concorda com as pessoas. A prova é uma medida de concordância: um lote de respostas rotulado por humanos e pelo juiz, e o kappa de Cohen, que desconta o acordo que aconteceria por acaso. Kappa acima de 0,8 é concordância forte: o juiz pode substituir a leitura em rotina; entre 0,6 e 0,8, serve para triagem; abaixo, ou a definição é ambígua ou o juiz é ruim. O experimento coloca você no papel do rotulador e calcula o seu kappa contra a referência, para sentir o que "definição operacional" significa.

Experimento · Rotule e meça a sua concordância

roda no navegador

Seis respostas, cada uma com os trechos citados. Marque "fiel" se tudo o que a resposta afirma está sustentado pelos trechos, "não fiel" se não. Ao fim, a matriz contra a referência e o kappa.

faça agora

Rotule sem reler o capítulo. Se o seu kappa ficou abaixo de 1, olhe as discordâncias: quase sempre são respostas "quase certas" (o número certo com um alcance a mais, "vale também para compras"). É exatamente o que a definição operacional precisa dizer com clareza, para pessoas e para o juiz: uma afirmação a mais sem sustentação torna a resposta não fiel.

Perguntas que aparecem aqui

Fidelidade e exatidão não são a mesma coisa?

Não. Fiel é "sustentada pelos trechos citados"; exata é "diz o mesmo que a referência". Uma resposta pode ser fiel e incompleta (cita e sustenta, mas deixa de fora metade), ou exata e não fiel (acertou de memória, sem citar). Para auditoria, fidelidade é a métrica inegociável; exatidão é útil para perguntas com resposta única.

Fiel = sustentada; exata = igual à referência.

Por que o kappa e não a concordância simples?

Porque se 90% das respostas são fiéis, um juiz que diz "fiel" para tudo concorda em 90% sem olhar nada. O kappa desconta esse acordo esperado pelo acaso: o mesmo juiz preguiçoso tem kappa zero. É o número que diz se o juiz está fazendo trabalho.

Concordância simples premia o juiz que não lê.

Quantas respostas rotular à mão para calibrar o juiz?

Algumas dezenas por tipo (com resposta, sem resposta, limite), rotuladas por duas pessoas (para saber a concordância entre humanos também; se elas discordam, a definição é o problema, não o juiz). Depois, uma amostra pequena por mês para conferir que o juiz não derivou.

Dezenas para calibrar; amostra mensal para vigiar.

Cobertura precisa da lista de achados dos auditores?

Precisa, e é o dado mais caro do conjunto: documentos reais com os achados que auditores apontaram, critério a critério. Sem essa lista, cobertura não existe; com ela, é código puro. O projeto começa com poucos documentos anotados e cresce com o uso, porque cada auditoria revisada é um documento anotado a mais.

Cobertura é cara de montar e barata de medir.

O juiz pode rotular o conjunto de teste do próprio juiz?

Não: seria avaliar um aluno com a prova que ele mesmo corrigiu. A referência para calibrar o juiz é humana; o juiz só entra depois de calibrado, e nunca avalia a própria calibração.

Referência humana para o juiz; juiz para o resto.

Escreva a definição operacional de fidelidade, cobertura e recusa correta, e explique com as suas palavras o que o kappa desconta.

Capítulo 5

O protocolo: como não se enganar

Uma medição vale pelo que impede. O protocolo do projeto tem seis regras, e cada uma bloqueia um jeito conhecido de produzir um número bonito e falso. Fixe as condições: temperatura 0, pensamento mínimo, mesmo modelo, mesma base, mesma versão de prompt; grave tudo no resultado. Rode três vezes: a variação entre execuções é a barra de erro mínima; uma métrica que oscila mais que a diferença entre versões não distingue as versões. Separe desenvolvimento de teste: itere olhando o dev; o teste só entra quando a versão está pronta, e o número do teste é o que se reporta. Nunca ajuste olhando o teste: cada olhada é uma iteração de ajuste disfarçada, e o teste vira dev. Meça sempre as mesmas coisas: as quatro métricas, no mesmo conjunto, com o mesmo código de medição versionado. Registre por versão: resultado ao lado da versão do prompt, do modelo, da base e do conjunto, para que uma regressão seja rastreável.

O jeito mais comum de se enganar é o sobreajuste ao conjunto: iterar o prompt até ele acertar as perguntas do dev, e concluir que ele melhorou. Com dev pequeno, boa parte do "ganho" é o prompt aprendendo as peculiaridades daquelas perguntas (uma palavra, um formato), e o teste não acompanha. O simulador mostra as duas curvas se separando conforme você itera, e como o tamanho do dev muda a inclinação.

Experimento · Simulador de sobreajuste

simulação

Você itera o prompt olhando o conjunto de desenvolvimento. A curva laranja é o que você vê (dev); a verde, o que o teste diria. Mova as iterações e o tamanho do dev.

faça agora

Com dev de 20 perguntas, vá de 0 a 30 iterações e veja a laranja subir para perto de 100% enquanto a verde para em 80% e começa a cair. Suba o dev para 200: a laranja passa a acompanhar a verde. Moral: iterar muito num dev pequeno produz um prompt que decorou o dev. É uma simulação, mas a forma é a que se observa na prática.

Perguntas que aparecem aqui

Três execuções em temperatura zero não são iguais?

Quase: a página 1 explicou que "zero" é "quase determinístico". Três execuções medem essa variação residual e a do provedor. Se as três dão o mesmo número, ótimo: a barra de erro é zero e você sabe disso. Se diferem, você sabe quanto, e uma diferença entre versões menor que isso não é diferença.

Três execuções compram a barra de erro mínima.

E se o teste for pequeno demais para dizer algo?

Então o número do teste vem com um intervalo largo (capítulo 7) e a decisão de "entra ou não" fica honesta: "não dá para afirmar que passou do alvo". A solução é o conjunto crescer, não olhar mais vezes para o mesmo teste.

Teste pequeno dá intervalo largo, não dá licença para espiar.

Posso reciclar o teste quando o dev esgota?

Uma vez por ciclo grande, com um teste novo montado a partir de casos novos (produção, analistas), o teste antigo pode virar dev. O que não pode é iterar no teste atual. A regra é que o número reportado vem de casos que ninguém usou para ajustar.

Teste antigo vira dev quando há teste novo.

O código de medição também precisa de versão?

Precisa: uma mudança na regra de "cita o esperado" (aceitar o caput quando o esperado é o inciso, por exemplo) muda todos os números. Sem versão do código de medição, uma melhoria de métrica pode ser uma mudança de régua.

Régua com versão; senão, o ganho pode ser a régua.

Escreva as seis regras do protocolo e, para cada uma, o jeito de se enganar que ela bloqueia.

Capítulo 6

A rodada completa: o Ex. 7 no navegador

Tudo junto: o conjunto (as 12 perguntas do guia, mais as quatro sem resposta, mais os casos que você salvou no capítulo 2) passa pela busca nas três variantes e, se você quiser, pela geração e validação. O painel mostra os números contra os alvos, com o intervalo de confiança do recall; a tabela mostra a posição do esperado em cada busca, pergunta a pergunta, e o que aconteceu na geração. Cada rodada fica registrada neste navegador com o rótulo dos parâmetros, para o capítulo 8 comparar.

Custo: um lote de embeddings para todas as perguntas (uma chamada) e, na geração, uma chamada por pergunta gerada. "Só a busca" não gasta geração nenhuma e já mede recall e MRR, que é a maior parte do Ex. 7.

Perguntas que aparecem aqui

Por que o recall da híbrida às vezes é menor que o da lexical numa pergunta?

Porque a fusão pode empurrar para baixo um trecho que só uma busca achou, se a outra trouxe muitos concorrentes. Na média a híbrida ganha; em perguntas isoladas, pode perder. É o que a tabela pergunta a pergunta mostra e a média esconde.

Média para decidir; tabela para entender.

Os meus casos do capítulo 2 contam igual aos do guia?

Contam: entram no mesmo conjunto, com o mesmo peso. Se um caso seu tiver o esperado errado, o recall cai por causa dele, e é assim que você descobre que o caso está errado: olhando a linha dele na tabela.

Caso errado aparece como "erro do sistema" até alguém olhar.

Fidelidade medida com 4 gerações vale alguma coisa?

Vale para ver o mecanismo, não para decidir: com n = 4 o intervalo vai de zero a um. O capítulo 7 mostra a conta. No Ex. 7 de verdade, a fidelidade se mede com dezenas de perguntas, e a cota gratuita é o limite prático; é um bom motivo para rodar a busca sempre e a geração por amostra.

Poucas gerações mostram o mecanismo; muitas dão o número.

A rodada registra os textos das respostas?

Aqui, só os resultados (posições, acertos, rótulo). No projeto, o registro guarda também os ids citados e a resposta, para a análise de erro do capítulo 7 e para o laço de volta. Registro sem detalhe só diz "caiu"; com detalhe diz "caiu nesta pergunta por este motivo".

Registro detalhado transforma número em diagnóstico.

Capítulo 7

Ler o número: intervalo de confiança e análise de erro

"Recall@12 de 83% em 12 perguntas" não é 83%: é "10 de 12", e 10 de 12 é compatível com um recall verdadeiro de 55% e com um de 95%. Toda proporção medida numa amostra vem com um intervalo de confiança, e com n pequeno ele é largo o bastante para engolir o alvo. O intervalo de Wilson (o que o guia usa; é bem comportado perto de 0 e 1) diz, para k acertos em n, a faixa onde o valor verdadeiro provavelmente está. A decisão "atingiu o alvo" só é defensável quando o limite inferior passa do alvo; até lá, "o ponto passa" é conversa.

A largura do intervalo cai com a raiz de n: de 12 para 48 perguntas, a largura cai pela metade; para 200, cai a um quarto. É a conta que dimensiona o conjunto: para afirmar recall ≥ 0,80 com um recall observado de 0,88, são necessárias em torno de 100 perguntas; com 0,84 observado, várias centenas. A calculadora faz a conta e o gráfico mostra a curva.

O outro lado da leitura é a análise de erro: o número diz quanto; a tabela pergunta a pergunta diz onde. Cortar os resultados por tipo (com/sem resposta), por artigo, por comprimento da pergunta, por fonte do caso, revela padrões que a média esconde: "a vetorial perde as perguntas com número de artigo", "a recusa indevida se concentra nos casos-limite". Cada padrão é um lugar para mexer, e cada lugar para mexer é uma hipótese para a próxima versão testar.

Perguntas que aparecem aqui

Por que Wilson e não "média ± 1,96 × desvio"?

O intervalo normal (Wald) quebra perto de 0 e 1 e com n pequeno: dá limites acima de 100% ou abaixo de 0, e é estreito demais quando a proporção é alta, que é exatamente o caso de fidelidade em 0,98. Wilson corrige isso; é a escolha padrão para proporções com n pequeno.

Wald mente perto das bordas; Wilson não.

Bootstrap é melhor?

Para proporções simples, Wilson basta e é fechado. Bootstrap (reamostrar o conjunto com reposição e recalcular a métrica milhares de vezes) é útil para métricas compostas (MRR, nDCG, índice) onde não há fórmula fechada, e para comparar versões. O Ex. 7 pode implementar em dez linhas de numpy.

Fórmula quando existe; bootstrap para o resto.

Com n pequeno, então, não vale medir?

Vale, com honestidade: reporte o ponto e o intervalo, e use o resultado para diagnóstico (análise de erro) mais que para decisão. O que não vale é reportar "83%" como se fosse um número, e decidir sobre ele.

n pequeno diagnostica; n grande decide.

O intervalo vale para fidelidade também?

Vale, e é onde ele mais surpreende: para afirmar fidelidade ≥ 0,98 com 95% de confiança, são necessárias centenas de respostas aceitas sem falha. É o motivo de a fidelidade ser medida continuamente (juiz por amostragem em produção) e não só numa rodada.

Alvo alto exige n grande para ser provado.

Capítulo 8

Comparar versões: pergunta a pergunta, não média contra média

"A v3 fez 86% e a v2 fez 83%" parece uma melhoria de três pontos. Em 30 perguntas, são três pontos que cabem dentro do intervalo das duas; a diferença pode ser acaso. A comparação certa é pareada: as duas versões responderam às mesmas perguntas, então olhe pergunta a pergunta e conte em quantas a v3 acertou e a v2 errou (vitórias), em quantas o contrário (derrotas) e em quantas as duas fizeram o mesmo (empates, que não informam nada). Se são 4 vitórias e 1 derrota em 30 perguntas, a v3 é melhor em 4 casos específicos e pior em 1; e o teste do sinal sobre os 5 pares discordantes diz se 4 a 1 é distinguível de cara ou coroa (com 5 pares, não é).

A comparação pareada também é a melhor análise de erro: as perguntas que mudaram de lado são exatamente as que a mudança de versão afetou. Ler essas perguntas (e não a média) diz se a v3 melhorou o que pretendia melhorar ou se ganhou por acaso em outro lugar e perdeu onde não devia. Uma regressão (pergunta que a v2 acertava e a v3 erra) é sempre digna de leitura, mesmo quando a média subiu.

Perguntas que aparecem aqui

O teste do sinal é rigoroso o bastante?

Para acertos binários (acertou/errou) pareados, o teste do sinal ou o de McNemar são os corretos e não assumem nada sobre a distribuição. São conservadores com poucos pares discordantes, o que é uma virtude: impedem de declarar vitória com 4 a 1. Para métricas contínuas (MRR), o bootstrap pareado é o equivalente.

Pareado e sem suposições: o rigor certo para acertos.

Muitos empates são um problema?

São informação: dizem que a mudança não tocou naquelas perguntas. Se quase tudo empata, a mudança é pequena, e o conjunto não tem casos onde ela importe. Ou ela não importa, ou faltam casos do tipo que ela deveria melhorar.

Empate diz onde a mudança não chega.

Uma versão pode "ganhar" no teste do sinal e ser pior?

Pode, se ganhar em perguntas fáceis e perder numa pergunta crítica (um critério de alto risco). Por isso o projeto olha, além do teste, a lista de regressões, e trata algumas perguntas como bloqueantes: se a versão nova erra uma delas, não entra, independentemente da média.

Estatística decide o comum; casos bloqueantes protegem o crítico.

Comparar contra qual referência: a versão anterior ou a primeira?

Contra a versão em produção (a que a candidata vai substituir). E, periodicamente, contra uma referência fixa (a v1), para ver a trajetória e detectar deriva lenta que comparações consecutivas não pegam (cada uma "sem diferença", a soma delas grande).

Capítulo 9

Avaliação contínua e o índice diante do auditor

A rodada do capítulo 6 é o que acontece antes de uma versão entrar. Depois que ela entra, a avaliação continua em três ritmos. A cada deploy: o conjunto de teste inteiro, com os quatro alvos como portão. Diariamente: um subconjunto de regressão rápida (dezenas de casos, só busca, custo zero de geração) que pega a mudança silenciosa do provedor ou da base (página 7, capítulo 9). Continuamente: o juiz por amostragem em produção, que mede fidelidade sobre respostas reais, e o contador de descartes. Os três alimentam o mesmo painel, com o mesmo código de medição versionado.

E há a medida que o cliente vê: o índice de conformidade. Ele é determinístico (25% por bloco; cada critério vale 100, 50 ou 0 conforme a classificação; NAO_AVALIAVEL não entra), calculado em código a partir da tabela de classificações. A pergunta que um auditor faz é "esse número significa o quê?", e a resposta honesta é uma medida de concordância: em documentos que auditores revisaram, critério a critério, em que fração a classificação do sistema coincide com a do auditor. Essa fração, com o seu intervalo, é o que sustenta o índice; sem ela, o índice é uma aritmética sobre palpites. As duas calculadoras abaixo mostram o índice e a concordância que ele precisa.

Perguntas que aparecem aqui

Por que NAO_AVALIAVEL não conta zero?

Porque "não deu para avaliar com este excerto" não é uma violação; contar como zero puniria o documento pela limitação do sistema e transformaria uma dúvida em um achado. Ele sai da média e aparece separado ("3 critérios não avaliáveis"), para o auditor olhar. Um bloco inteiro não avaliável não entra no índice, e o relatório diz isso.

Dúvida se reporta; não se pontua.

Pesos iguais entre blocos (25%) fazem sentido?

É o ponto de partida definido com o cliente, por simplicidade e transparência. Pesos diferentes por bloco, ou por critério, são possíveis e ficam em configuração, não em código; qualquer peso precisa ser explicável ao auditor, e "25% cada" é o mais fácil de explicar. A concordância com o parecer humano é o que diz se a ponderação precisa mudar.

Simples e explicável primeiro; ponderação quando a medida pedir.

Concordância de 93% é boa?

Depende do n e de onde estão os 7%: se estão em ALERTA contra CONFORME (o sistema foi mais cauteloso), é aceitável; se estão em CONFORME contra NAO_CONFORME (o sistema absolveu uma violação), é grave mesmo em 3%. A matriz de confusão por classe, não só a fração, é o que se apresenta.

Olhe a matriz: discordâncias não são todas iguais.

O que vai no painel de avaliação contínua?

As quatro métricas do teste por versão (uma linha por deploy); a regressão diária (uma curva); a fidelidade amostral e os descartes por motivo (curvas diárias); a concordância com auditores acumulada (com intervalo). E as versões de tudo, para que qualquer ponto do painel seja rastreável até um commit.

Painel é histórico com versões; sem elas é decoração.

Quem é o dono da avaliação no projeto?

Uma pessoa: dona do conjunto (o que entra, quem revisa), do código de medição (versão) e do painel. Sem dono, o conjunto envelhece, o código muda de régua e os alvos viram sugestão. É o mesmo papel que uma equipe dá a testes automatizados de software.

Capítulo 10

No projeto, checklist e autoavaliação

No projeto

O conjunto de avaliação vive em avaliacao/, versionado: casos_v3.jsonl (pergunta, tipo, esperado, resposta de referência, origem, revisor), dividido em dev e teste por um campo, com dezenas de casos por critério e os quatro tipos. O código de medição (avaliar.py) é versionado junto e calcula, para uma configuração congelada (modelo, base, prompt, parâmetros da busca): recall@k e MRR das três buscas; fidelidade, cobertura, recusa correta e recusa indevida sobre as gerações; intervalos de Wilson; e a comparação pareada contra a versão em produção. A rodada roda três vezes; o resultado vai para resultados/<versao>.json e para o painel. Portão de deploy: os quatro alvos no teste, nenhum caso bloqueante regredido. Em produção: regressão diária só de busca, juiz por amostragem, contador de descartes, e a concordância com auditores acumulada por documento revisado, que é o que sustenta o índice de conformidade.

O Ex. 7 (VIN-11) é o avaliar.py em pequeno: ler o JSONL, rodar as três buscas no pgvector do Ex. 3, calcular recall@k e MRR com intervalo, gerar para uma amostra e medir fidelidade e recusa, e gravar o resultado com as versões.

Código de referência

# avaliacao/avaliar.py — métricas de busca e de resposta com intervalo (Ex. 7)
import json, math, statistics
from collections import Counter

def wilson(k: int, n: int, z: float = 1.96) -> tuple[float, float]:
    if n == 0: return (0.0, 1.0)
    p = k / n; d = 1 + z * z / n
    c = (p + z * z / (2 * n)) / d; h = z * math.sqrt(p * (1 - p) / n + z * z / (4 * n * n)) / d
    return (max(0.0, c - h), min(1.0, c + h))

def carregar(caminho: str, particao: str) -> list[dict]:
    casos = [json.loads(l) for l in open(caminho, encoding="utf-8")]
    return [c for c in casos if c.get("particao", "dev") == particao]

def posicao(lista_ids: list[str], esperado: list[str]) -> int | None:
    for i, cid in enumerate(lista_ids, 1):
        if cid in esperado: return i
    return None

def metricas_busca(casos: list[dict], buscar, k: int = 12) -> dict:
    """buscar(pergunta) -> {'vetorial': [ids], 'lexical': [ids], 'hibrida': [ids]}"""
    com = [c for c in casos if c["tipo"] == "com"]
    out = {}
    for nome in ("vetorial", "lexical", "hibrida"):
        acertos, rr = 0, 0.0
        for c in com:
            p = posicao(buscar(c["pergunta"])[nome], c["esperado"])
            if p and p <= k: acertos += 1
            if p: rr += 1 / p
        lo, hi = wilson(acertos, len(com))
        out[nome] = {"recall@k": acertos / len(com), "ic95": (lo, hi), "mrr": rr / len(com), "n": len(com)}
    return out

def metricas_resposta(casos: list[dict], responder, julgar=None) -> dict:
    """responder(pergunta) -> {'ok', 'sem_evidencia', 'citacoes', 'resposta'}; julgar opcional (juiz calibrado)."""
    com = [c for c in casos if c["tipo"] == "com"]; sem = [c for c in casos if c["tipo"] == "sem"]
    fiel = aceitas = recusa_ind = 0
    for c in com:
        r = responder(c["pergunta"])
        if r["sem_evidencia"]: recusa_ind += 1; continue
        if not r["ok"]: continue
        aceitas += 1
        cita = any(cid in c["esperado"] for cid in r["citacoes"])
        sustentada = julgar(r["resposta"], r["citacoes"]) if julgar else True
        if cita and sustentada: fiel += 1
    recusa_ok = sum(1 for c in sem if responder(c["pergunta"])["sem_evidencia"])
    return {
        "fidelidade": {"valor": fiel / aceitas if aceitas else None, "ic95": wilson(fiel, aceitas), "n": aceitas},
        "recusa_correta": {"valor": recusa_ok / len(sem) if sem else None, "ic95": wilson(recusa_ok, len(sem)), "n": len(sem)},
        "recusa_indevida": {"valor": recusa_ind / len(com), "n": len(com)},
    }

def comparar_pareado(acertos_a: list[int], acertos_b: list[int]) -> dict:
    vit = sum(1 for a, b in zip(acertos_a, acertos_b) if b > a); der = sum(1 for a, b in zip(acertos_a, acertos_b) if a > b)
    n = vit + der
    p = min(1.0, 2 * sum(math.comb(n, i) for i in range(0, min(vit, der) + 1)) / 2 ** n) if n else 1.0   # teste do sinal
    return {"vitorias_b": vit, "derrotas_b": der, "empates": len(acertos_a) - n, "p_sinal": p}

def rodada(casos, buscar, responder, versoes: dict, k=12, repeticoes=3) -> dict:
    execs = [metricas_busca(casos, buscar, k) for _ in range(repeticoes)]
    recall_h = [e["hibrida"]["recall@k"] for e in execs]
    res = {"versoes": versoes, "k": k, "busca": execs[0], "variacao_recall_h": (min(recall_h), max(recall_h)),
           "resposta": metricas_resposta(casos, responder)}
    json.dump(res, open(f"resultados/{versoes['prompt']}_{versoes['base']}.json", "w"), ensure_ascii=False, indent=2)
    return res
