Alucinação, validação e guardrails

O modelo continua texto provável, e provável não é verdadeiro (página 1). Num sistema de auditoria isso não pode chegar ao analista sem passar por barreiras. Capítulo 1

Os oito jeitos de errar

"Alucinação" é um nome só para falhas de natureza diferente, e tratá-las como uma coisa só é o primeiro erro. Num RAG com citações, uma resposta errada cabe em um destes tipos. Fabricação sem fonte: o modelo responde do próprio treinamento, sem citar (o valor da Lei 8.666, por exemplo). Citação inexistente: cita um id que não existe na base. Citação fora do contexto: cita um id que existe, mas não estava entre os trechos enviados naquela chamada; ele "lembrou" de outra chamada, ou inventou um id plausível. Distorção: cita o trecho certo e troca o número, o prazo, o percentual. Afirmação não sustentada: a citação é boa para uma parte da resposta, e outra parte não tem trecho nenhum. Recusa indevida: o trecho certo estava lá e o modelo disse "sem evidência". Incoerência: responde e ao mesmo tempo marca sem_evidencia. Formato inválido: texto solto, JSON quebrado, enum fora da lista.

A distinção importa porque cada tipo tem uma camada que o pega, e camadas diferentes custam diferente: cinco dos oito são pegos por código puro, sem chamada nenhuma; dois exigem que alguém (ou o juiz) leia o texto; um só aparece na medição contra o conjunto de avaliação. A galeria abaixo treina o olho: oito saídas para a mesma pergunta, com os mesmos quatro trechos no contexto.

Perguntas que aparecem aqui

Por que citação fora do contexto é diferente de inexistente?

Porque o id existe na base, então uma verificação ingênua ("o id existe?") passa. A verificação certa é "o id estava entre os trechos desta chamada?". Um modelo que cita algo que não recebeu está usando memória ou inventando um id plausível, e as duas coisas quebram a rastreabilidade: o analista abriria um trecho que o modelo nunca leu.

A pergunta certa é "estava no contexto", não "existe".

Distorção é o mais perigoso?

Para texto legal, sim. A citação está certa, o trecho está certo, e o número está errado: quem confere a fonte por alto confirma a resposta. Por isso o projeto tem uma verificação específica de números contra o trecho citado (capítulo 7), além do juiz.

Erro pequeno com fonte certa engana melhor.

Recusa indevida é "alucinação"?

Não no sentido comum, mas é uma falha com o mesmo custo prático: o analista não recebe uma resposta que a base tinha. Aparece quando a instrução de recusa é forte demais, quando o trecho certo ficou em posição ruim no contexto, ou quando o modelo não reconheceu a resposta na redação legal. Só se mede com o conjunto de avaliação, e é por isso que a taxa de recusa se mede nas duas direções (capítulo 5).

Recusar o que a base responde é erro; meça as duas direções.

Escreva os oito tipos, com um exemplo de cada, e marque quais se detectam pela estrutura do JSON e quais exigem ler o texto.

Capítulo 2

Camadas: nenhuma segura tudo, juntas seguram quase tudo

A resposta do modelo passa por uma sequência de barreiras, cada uma barata de um jeito e cega de outro. Busca boa (páginas 2 a 4): se o trecho certo não chega ao contexto, nenhuma camada posterior conserta; recall alto é a primeira defesa contra fabricação e recusa indevida. Esquema de saída: elimina o formato inválido antes de o JSON ser lido. Validação em código: confere ids, contexto, coerência, tamanho; determinística, custo zero, pega cinco dos oito tipos. Verificação numérica: todo número, percentual ou valor da resposta precisa aparecer no trecho citado. Juiz de aderência: um modelo relê resposta e trechos e diz, afirmação por afirmação, o que é sustentado; custa uma chamada, pega o que só se vê lendo. Conjunto de avaliação em rotina (página 8): a única forma de ver recusa indevida e degradação silenciosa. Parecer humano: no projeto, a IA não decide; o auditor lê classificação, evidência e base legal e dá o parecer.

A ordem também é custo: as camadas baratas vêm antes, e uma resposta rejeitada pela validação não gasta o juiz. A matriz abaixo mostra o que passa quando você desliga uma camada. Repare que o parecer humano pega tudo em tese; na prática, um auditor com quarenta critérios por documento confia no que o sistema lhe entrega, e é por isso que as camadas automáticas existem.

Perguntas que aparecem aqui

Por que o juiz não roda sempre no projeto?

Custo: uma chamada a mais por critério dobra o gasto da auditoria. Ele roda por amostragem (uma fração das respostas, para medir a taxa de afirmações não sustentadas) e nos critérios marcados como de alto risco. Se a amostragem mostrar taxa alta, a resposta é melhorar o prompt ou a busca, não ligar o juiz para tudo.

Juiz mede e protege o crítico; não substitui as camadas baratas.

Uma camada pode rejeitar respostas boas?

Pode, e isso também se mede: a verificação numérica rejeita uma resposta que arredondou ("cerca de 100 mil"), a de tamanho rejeita uma resposta longa e certa. Cada rejeição vai para o contador por motivo (capítulo 3), e um motivo que cresce sem que a qualidade caia é sinal de regra rígida demais. Regras se ajustam com o conjunto de avaliação, como prompts.

Falso positivo da validação é medível e ajustável.

Onde entra a temperatura zero nisso?

É uma camada de estabilidade, não de verdade: reduz a variação entre chamadas, o que torna as outras camadas mensuráveis (um erro que aparece uma vez em dez é difícil de caçar). Não impede nenhum dos oito tipos.

Determinismo ajuda a medir; não corrige.

Liste as sete camadas na ordem, com o custo de cada uma e o tipo de falha que ela é a única a pegar.

Capítulo 3

Validação em código e o contador de descartes

A validação é uma função pura: recebe o JSON do modelo e a lista de ids que foram enviados no contexto, devolve aceita ou rejeitada e um dicionário de motivos. As regras do projeto, na ordem em que rodam: malformado (não é o objeto do esquema); fonte_inexistente (id que não está na base); fora_do_contexto (id que não estava nesta chamada); sem_citacao (responde sem nenhuma citação válida e sem sem_evidencia); incoerente (sem_evidencia com citações e texto que responde); numero_sem_fonte (valor, percentual ou prazo da resposta que não aparece no texto dos trechos citados); muito_longa. Uma resposta aceita é a que tem pelo menos uma citação válida e nenhum motivo bloqueante, ou uma recusa coerente.

O contador de descartes por motivo é o entregável do Ex. 6 e o painel mais útil da operação: um motivo que sobe é um sintoma com nome. fora_do_contexto subindo depois de uma troca de modelo diz que o modelo novo "lembra" ids; numero_sem_fonte alto num critério diz que o prompt daquele critério induz arredondamento; sem_citacao crescendo diz que a busca piorou ou o prompt afrouxou. Sem o contador, tudo isso é "a qualidade caiu".

Perguntas que aparecem aqui

O que fazer com uma resposta rejeitada?

Uma nova tentativa, com o motivo no prompt ("a citação X não estava no contexto; use apenas os ids fornecidos"), e só uma. Se falhar de novo, a pergunta fica como "sem resposta válida" com o motivo, visível ao analista, e o caso vai para o registro. Duas tentativas resolvem a maioria dos formatos e ids errados; o que resiste é sinal de problema no prompt ou na busca.

Uma repetição informada; depois, registrar e seguir.

A verificação de números não é rígida demais?

É rígida de propósito para valores, percentuais e prazos: em texto legal, o número é a resposta. Ela ignora números pequenos (artigos, incisos) e aceita variações de formato por normalização ("100.000,00" e "100000"). O que ela rejeita e não deveria (arredondamentos, extenso) entra no contador e ajusta a regra ou o prompt ("copie os valores como estão no trecho").

Rígida onde o número é a resposta; ajustável pelo contador.

Validar custa tempo?

Microssegundos: é código sobre um JSON pequeno. É a camada mais barata do sistema, e por isso roda em toda resposta, antes de qualquer outra coisa.

Grátis, determinística, primeira.

Capítulo 4

O juiz de aderência

A validação em código confere estrutura, fontes e números, e não lê. "O limite é R$ 100.000,00 e a garantia nesses casos é dispensada" passa em todas as regras: cita o art. 75, I (existe, está no contexto), o número está no trecho, é curta. A segunda metade da frase não está em trecho nenhum. Para pegar isso é preciso ler resposta e trechos juntos, e é o que o juiz de aderência faz: uma segunda chamada, com prompt próprio (biblioteca, juiz_v1), que recebe a resposta e os mesmos trechos, quebra a resposta em afirmações e diz, para cada uma, se algum trecho a sustenta e qual. O veredito é um enum: SUSTENTADA, PARCIAL, NAO_SUSTENTADA.

Três cuidados para o juiz não virar mais uma fonte de erro. O juiz não corrige, só verifica: um juiz que reescreve a resposta é um segundo gerador. O juiz recebe os mesmos trechos da chamada original, nunca mais: se ele buscasse outros, estaria julgando contra um contexto que a resposta não viu. E o juiz também é validado em código: os ids que ele cita precisam estar no contexto; o veredito precisa ser coerente com as afirmações. Um juiz é um modelo com um prompt, com todas as falhas dos modelos; a diferença é que a tarefa dele é mais fácil (comparar dois textos) que a original (responder), e modelos erram menos em tarefas fáceis.

No projeto o juiz roda por amostragem (para medir a taxa de afirmações não sustentadas, que é a "fidelidade" da página 8) e nos critérios de alto risco, atrás de flag. A alternativa mais barata, um modelo pequeno de inferência textual (NLI) local, faz o mesmo trabalho com menos flexibilidade; para o volume do projeto, o modelo de linguagem com esquema é suficiente e mais explicável.

Perguntas que aparecem aqui

O juiz pode ser o mesmo modelo que gerou a resposta?

Pode, e no projeto é, por simplicidade e custo. O viés de "concordar consigo mesmo" existe, mas é menor do que parece quando a tarefa é comparar textos com esquema fechado. Um modelo diferente para o juiz é uma melhoria possível, medida na página 8; não é pré-requisito.

Mesmo modelo, tarefa diferente, esquema fechado: funciona.

PARCIAL é aceito ou rejeitado?

Depende do critério. Para a resposta ao analista, PARCIAL vira uma resposta com as afirmações não sustentadas removidas ou marcadas, e o registro conta. Para um critério de auditoria de alto risco, PARCIAL rejeita e o critério fica NAO_AVALIAVEL com motivo. A política é por critério, definida com quem audita.

Política por critério; o juiz só informa.

Quanto o juiz custa por documento?

Se rodasse em tudo, tantas chamadas quantos critérios (40), cada uma com os trechos de novo: dobra o custo. Por amostragem de 10%, custa 4 chamadas por documento e dá uma medida contínua de fidelidade. É o arranjo do projeto.

Amostragem compra a medida sem dobrar a conta.

Capítulo 5

Recusar bem: a matriz 2×2

Um sistema que nunca recusa inventa; um que recusa demais é inútil. As duas falhas se medem juntas, numa matriz: perguntas com resposta na base (o modelo deve responder) e sem resposta (deve recusar), contra o que ele fez. Recusa correta (não tinha, recusou) e resposta correta (tinha, respondeu) são a diagonal boa; inventou (não tinha, respondeu) e recusa indevida (tinha, recusou) são as falhas. O alvo do projeto é recusa correta acima de 0,90 com recusa indevida próxima de zero, e as duas metas só se medem com um conjunto que tenha perguntas sem resposta de propósito (página 8).

Três alavancas movem a matriz. A instrução de recusa (página 6): forte demais, sobe a recusa indevida; fraca, sobe a invenção. Um limiar de busca: se o melhor score da vetorial está muito abaixo da faixa típica (página 2) e a lexical não achou nenhum termo, o sistema pode recusar antes de gerar, economizando a chamada; o limiar se calibra com a matriz. E o reranker ou juiz: nota baixa em todos os candidatos é sinal de ausência. A recusa também precisa ser útil: "sem evidência" seco não ajuda; "os trechos tratam de garantia mas não do prazo de validade da certidão" diz ao analista onde procurar.

Perguntas que aparecem aqui

Por que "sem evidência" e não "não sei"?

Porque "sem evidência" é uma afirmação sobre a base ("os trechos fornecidos não respondem"), verificável, e "não sei" é uma afirmação sobre o modelo, que não se verifica. A primeira diz ao analista o que fazer: ampliar a busca, olhar outra norma, perguntar diferente.

Recusa é um fato sobre o contexto, não sobre o modelo.

Recusar antes de gerar não esconde perguntas que o modelo responderia?

Se o limiar for agressivo, sim: é recusa indevida por outro caminho, e entra na mesma matriz. O limiar de busca deve ser conservador (recusar só quando a busca claramente não achou nada) e calibrado com perguntas sem resposta reais, não inventadas para parecer fáceis.

Limiar conservador; calibre com casos reais.

Como criar perguntas sem resposta boas?

Perguntas plausíveis do domínio cuja resposta está em outra norma que não está na base (ISS, FGTS, previdência) ou em dados que a base não tem (números de um edital). Perguntas absurdas ("qual a cor do edital?") são fáceis demais e não medem nada. A página 8 dedica uma seção a isso.

Sem resposta, mas plausível: é o que aparece em produção.

Capítulo 6

Injeção: detectar, escapar, sinalizar

A página 6 mostrou a injeção por documento e as camadas no prompt. Esta seção é a parte do código: o que o sistema faz com o texto antes de ele entrar no prompt e depois de a resposta sair. Escapar: todo conteúdo que vai entre tags passa por escape de <, > e &, para que um documento contendo </excerto> não feche a tag por dentro. Detectar: um conjunto de padrões (ordens para ignorar instruções, texto endereçado "ao sistema", tentativa de fixar a classificação, tags do prompt dentro do documento, caracteres invisíveis, apelos a autoridade) marca o trecho com um sinal. Sinalizar, não editar: o texto vai inteiro ao modelo, escapado, com o sinal como atributo; o analista vê o sinal na interface e o registro conta. Editar o documento seria destruir a evidência de que ele tentou.

A detecção por padrões é reconhecidamente incompleta: injeções sutis não usam "ignore". Ela existe para pegar o óbvio de graça e para gerar casos de teste; a defesa contra o sutil é o conjunto das camadas (esquema, evidência literal, validação, juiz, parecer humano). E há um efeito colateral bom: um trecho de edital que fala com "o sistema de análise" é, por si, um achado para o auditor.

Perguntas que aparecem aqui

Escapar não confunde o modelo (ele vê &lt; em vez de <)?

Um pouco, em texto que tem muitos sinais de menor e maior (raro em edital). O ganho (o documento não consegue fechar a tag) vale a leve estranheza. Caracteres invisíveis são reais?

São: texto em branco sobre fundo branco, fonte tamanho 1, caracteres de largura zero, tudo sobrevive à extração do PDF e chega ao prompt sem ser visto por quem lê o documento. A extração (página 9) remove caracteres de controle, e o detector marca os que sobrarem.

O que a extração traz, o modelo lê; limpe e marque.

Devo bloquear o documento quando há injeção?

Não: analise, sinalize e registre. Bloquear dá ao documento o poder de impedir a própria auditoria. O sinal vai ao auditor como um achado, e a classificação segue com as camadas de sempre.

Injeção é achado, não bloqueio.

Capítulo 7

Números, prazos e identificadores: a verificação que mais pega

Em texto legal a resposta costuma ser um número: um valor, um percentual, um prazo em dias, um artigo. E é exatamente o que os modelos mais distorcem (página 2 explicou por quê: números são detalhe de superfície para o vetor e para o modelo). A verificação numérica do validador é simples e devastadora: extrai da resposta todo valor monetário, percentual e número com mais de dois dígitos, normaliza (espaços, separadores) e exige que cada um apareça no texto dos trechos citados. Não apareceu, motivo numero_sem_fonte, rejeitada, nova tentativa com a instrução de copiar os valores como estão.

Dois refinamentos que o projeto usa. Números pequenos (um ou dois dígitos) não são checados por substring, porque "75" pode ser o artigo e "10" pode ser o inciso ou os dias; esses passam pelo parser de referências (página 5), que converte "art. 75, I" em id e confere se o id está nas citações. Datas e prazos em extenso ("dez dias úteis") são normalizados para número antes da comparação. O que não se resolve por regra ("cerca de cem mil") é rejeitado e vira instrução no prompt: "copie os valores exatamente como constam no trecho".

Perguntas que aparecem aqui

E se o trecho tiver o número por extenso e a resposta em algarismos?

A lei costuma trazer os dois ("R$ 100.000,00 (cem mil reais)"), então o algarismo casa. Quando só há extenso, a normalização converte antes de comparar (um dicionário pequeno cobre "dez", "quinze", "trinta", "cem mil"). O que sobrar rejeita e conta, e o contador diz se vale ampliar o dicionário.

Normalize os dois lados; o resto o contador mostra.

A verificação pega um número certo atribuído ao contexto errado?

Não: se a resposta diz "o prazo para compras é 10 dias úteis" e o trecho citado é o de obras (que também diz 10), o número casa. Esse é o caso do juiz (capítulo 4): sustentação lógica, não presença de string. As duas verificações se complementam.

Substring pega o número errado; o juiz pega o número certo no lugar errado.

Vale usar isso também na ingestão?

Vale: conferir que os números do trecho limpo são os mesmos do texto bruto pega erros de extração (um "1" que virou "l", um "0" que virou "O") antes de eles entrarem na base. É barato e roda uma vez por documento.

A mesma regra protege a entrada e a saída.

Descreva a verificação numérica (o que extrai, como normaliza, o que exige), os dois refinamentos e o caso que ela não pega.

Capítulo 8

Guardrails de entrada e de saída

Além de verificar se a resposta é verdadeira, o sistema verifica se ela é apropriada: se a pergunta cabe no escopo e se a saída respeita o papel da IA no projeto. Na entrada: a pergunta é sobre o domínio (licitações, contratos, o documento em análise)? Tem tamanho razoável? Contém dados pessoais que não deveriam ir ao provedor? Uma pergunta fora do escopo recebe uma resposta fixa, sem chamada; uma com CPF ou nome de pessoa física recebe mascaramento antes de sair da máquina, e o registro guarda que houve mascaramento. Na saída: o texto que chega ao analista não pode conter linguagem de parecer. A decisão do projeto é clara: a IA aponta indícios, classifica e cita; o auditor decide. "O edital deve ser reprovado", "recomendo a anulação", "é ilegal" são decisões, e saem da resposta antes de ela ser exibida, seja por rejeição e nova tentativa, seja por mostrar ao analista só os campos estruturados (classificação, evidência, base legal) e não a prosa.

Guardrails de saída também cobrem vazamento (a resposta não repete dados pessoais do documento além do necessário), escopo (não opina sobre o que não foi perguntado) e tamanho. São regras de código, com motivo próprio no contador (parecer_final, fora_do_escopo, dado_pessoal), e o detector abaixo mostra a mais importante para o projeto.

Perguntas que aparecem aqui

Por que não deixar o modelo dizer "reprovado" se a evidência é clara?

Porque o parecer é ato do auditor, com responsabilidade; a IA é auxílio. Um "reprovado" gerado por modelo numa tela cria a impressão de decisão tomada, e o auditor tende a confirmar em vez de avaliar. A classificação NAO_CONFORME com evidência e base legal diz o mesmo sem usurpar a decisão.

Indício com evidência, não veredito; o papel é do auditor.

Mascarar dados pessoais na entrada não quebra a análise?

Raramente: o critério de auditoria não depende do nome do responsável ou do CPF do licitante, e um marcador ("[PESSOA_1]") preserva a estrutura. Onde o dado importa (validade de uma certidão em nome de alguém), a análise usa o marcador e o auditor vê o original na interface, que nunca saiu da máquina.

Marcador preserva a análise; o dado fica em casa.

Guardrail de escopo rejeita perguntas legítimas?

Se for uma lista de palavras, sim. O projeto usa uma regra frouxa (a pergunta menciona algo do domínio ou do documento) e deixa o resto para a recusa com evidência: uma pergunta fora do escopo não acha trechos e recebe "sem evidência" com explicação. Guardrail de entrada é para o óbvio (tamanho, dados pessoais), não para adivinhar intenção.

Entrada: o óbvio; escopo real: a recusa com evidência.

Capítulo 9

Operar a validação: limiares, alertas e o laço de volta

A validação produz números todo dia: taxa de rejeição total e por motivo, taxa de recusa, resultado do juiz por amostragem. Operar é olhar para esses números com um limiar de alerta e um procedimento. A taxa de rejeição de um sistema estável fica numa faixa (uns poucos por cento, dependendo da rigidez das regras); quando sai da faixa, algo mudou: o modelo (o provedor atualizou), a base (uma carga nova), o prompt (um deploy), ou os documentos (um órgão novo com editais diferentes). O painel simulado abaixo mostra o que uma mudança de modelo faz com a taxa e como o limiar decide em quantos dias o alerta dispara.

O laço de volta fecha o ciclo: toda rejeição com motivo, toda recusa indevida encontrada por um analista, toda injeção detectada, toda afirmação que o juiz derrubou vira um caso no conjunto de avaliação (página 8), com a saída esperada revisada. O conjunto cresce com o que o sistema errou em produção, que é exatamente o que o próximo prompt ou o próximo modelo precisa provar que acerta. Sem o laço, a operação apaga incêndios; com ele, cada incêndio vira um teste.

Experimento · Painel de rejeições e limiar de alerta

simulação

faça agora

Baixe o limiar até disparar antes do dia 21: é o alarme falso que faz a equipe ignorar alertas. Suba até nunca disparar: a troca de modelo passa em silêncio. Ache o limiar que dispara em um ou dois dias depois da mudança e nunca antes. Depois pense: que outra medida dispararia mais cedo? (A rotina do conjunto de avaliação, no dia 21, se rodar diariamente.)

Perguntas que aparecem aqui

Limiar por motivo ou total?

Os dois: o total pega mudanças grandes; por motivo, mudanças específicas (fora_do_contexto subindo sozinho é um modelo novo "lembrando" ids; numero_sem_fonte subindo num critério é um prompt). Limiares por motivo são mais sensíveis e mais explicáveis.

Total para o grande; por motivo para o específico.

Quem revisa os casos que viram teste?

Alguém do domínio escreve a saída esperada; alguém da engenharia registra o caso no conjunto com a versão em que foi encontrado. Um caso sem saída esperada revisada não entra: seria testar contra um palpite.

Caso de teste é dado revisado, não log copiado.

Fixar a versão do modelo resolve a deriva?

Quando o provedor oferece versões fixas, ajuda, e o projeto fixa. Mas versões fixas são descontinuadas, e a troca acaba acontecendo. O que resolve é o conjunto de avaliação em rotina, que transforma "o provedor mudou algo" em "o recall caiu 4 pontos no dia 21", com o rastro dizendo qual versão respondeu.

Fixe quando puder; meça sempre.

Capítulo 10

No projeto, checklist e autoavaliação

No projeto

Toda resposta do ia-worker passa, nesta ordem, por: esquema de saída (na chamada); validação em código (validar_resposta para perguntas, validar_classificacao para critérios: ids existem, ids no contexto, coerência, números contra os trechos citados, evidência literal, tamanho, linguagem de parecer); uma nova tentativa com o motivo se rejeitada; juiz de aderência por amostragem de 10% e nos critérios marcados como de alto risco; guardrails de entrada (tamanho, mascaramento de dados pessoais) e de saída (parecer, escopo). Cada rejeição incrementa o contador por motivo, gravado com a versão do prompt, do modelo e da base; o painel tem limiar por motivo e total; alertas abrem uma revisão que termina com casos novos no conjunto de avaliação. A interface do analista mostra os campos estruturados (classificação, evidência, base legal, sinal de injeção, vigência do trecho), não a prosa do modelo, e o parecer é campo do auditor.

# validacao/resposta.py — validação em código com contador de descartes (Ex. 6)
import re, unicodedata
from collections import Counter
from dataclasses import dataclass, field

MOTIVOS = ("malformado", "fonte_inexistente", "fora_do_contexto", "sem_citacao", "incoerente", "numero_sem_fonte", "muito_longa", "parecer_final")
RE_NUM = re.compile(r"\d[\d.,]*\s*%|R\$\s*[\d.,]+|\b\d+(?:[.,]\d+)?\b")
RE_PARECER = re.compile(r"\b(deve ser|está) (reprovad|aprovad|anulad)|\brecomendo\b|\b(anulação|suspensão)\b|\bilegal\b|\bviola\b", re.I)
RE_RECUSA = re.compile(r"não (há|consta|trata|contém)|faltou|sem evid", re.I)

def norm(s: str) -> str:
    s = unicodedata.normalize("NFD", s.lower()); s = "".join(c for c in s if not unicodedata.combining(c))
    return re.sub(r"\s+", "", s)

@dataclass
class Resultado:
    ok: bool; motivos: Counter = field(default_factory=Counter); citacoes_ok: list = field(default_factory=list); sem_evidencia: bool = False

def validar_resposta(obj: dict | None, contexto_ids: list[str], base_ids: set[str], trechos: dict[str, str]) -> Resultado:
    r = Resultado(ok=False)
    if not isinstance(obj, dict) or not isinstance(obj.get("resposta"), str) or not isinstance(obj.get("citacoes"), list):
        r.motivos["malformado"] += 1; return r
    for c in obj["citacoes"]:
        cid = (c or {}).get("id")
        if cid not in base_ids: r.motivos["fonte_inexistente"] += 1
        elif cid not in contexto_ids: r.motivos["fora_do_contexto"] += 1
        else: r.citacoes_ok.append(cid)
    r.sem_evidencia = bool(obj.get("sem_evidencia"))
    if not r.sem_evidencia and not r.citacoes_ok: r.motivos["sem_citacao"] += 1
    if r.sem_evidencia and r.citacoes_ok and not RE_RECUSA.search(obj["resposta"]): r.motivos["incoerente"] += 1
    texto_citado = norm(" ".join(trechos[i] for i in r.citacoes_ok))
    for n in RE_NUM.findall(obj["resposta"]):
        n = n.strip(" .,")
        if re.fullmatch(r"\d{1,2}", n): continue                      # artigos e incisos: parser de referências
        if norm(n) not in texto_citado: r.motivos["numero_sem_fonte"] += 1
    if len(obj["resposta"]) > 900: r.motivos["muito_longa"] += 1
    if RE_PARECER.search(obj["resposta"]): r.motivos["parecer_final"] += 1
    bloqueantes = {"malformado", "sem_citacao", "incoerente", "numero_sem_fonte", "muito_longa", "parecer_final"}
    r.ok = (not any(r.motivos[m] for m in bloqueantes)) and (r.sem_evidencia or bool(r.citacoes_ok))
    return r

class Contador:
    """Descartes por motivo, com a versão de prompt/modelo/base para o painel."""
    def __init__(self): self.total = 0; self.rejeitadas = 0; self.por_motivo = Counter()
    def registrar(self, r: Resultado, versoes: dict) -> None:
        self.total += 1
        if not r.ok: self.rejeitadas += 1
        self.por_motivo.update(r.motivos)
        registrar_evento({"ok": r.ok, "motivos": dict(r.motivos), **versoes})   # uma linha por resposta
    def relatorio(self) -> str:
        taxa = self.rejeitadas / self.total if self.total else 0
        linhas = [f"{self.total} respostas · {self.rejeitadas} rejeitadas ({taxa:.1%})"]
        linhas += [f"  {m}: {n}" for m, n in self.por_motivo.most_common()]
        return "\n".join(linhas)
