Capítulo 1

O ciclo de consulta, etapa por etapa

RAG, retrieval-augmented generation, é um nome grande para uma sequência curta: a pergunta chega; a busca escolhe os trechos; os trechos e a pergunta viram um prompt; o modelo escreve a resposta citando os trechos; um código confere se as citações existem e estão no que foi enviado. Cinco etapas, duas chamadas de rede (uma de embedding, uma de geração), tudo o mais determinístico. O que torna o sistema confiável não é nenhuma etapa isolada; é que cada uma tem uma saída inspecionável e uma medida própria.

Repare no que não está no ciclo: nenhum treinamento, nenhuma memória entre perguntas, nenhuma decisão do modelo sobre o que buscar. No projeto o ciclo é determinístico e auditável de propósito: o mesmo documento, a mesma base e o mesmo prompt produzem os mesmos trechos, e a resposta só é aceita se as citações resistirem à validação. Variantes em que o modelo decide os passos (RAG "agêntico") existem, e o capítulo 2 diz quando fazem sentido; para auditar conformidade, previsibilidade vale mais que autonomia.

Perguntas que aparecem aqui

Por que a busca trouxe trechos para uma pergunta que a base não responde?

Porque busca é ranking: sempre existe um "mais próximo", mesmo que longe. A busca não sabe dizer "nada serve"; quem decide isso é o modelo, lendo os trechos, e a validação confere que ele não citou nada fora. Um limiar de score (página 2) ou a nota do reranker (página 4) podem antecipar a recusa e economizar a geração.

Ranking sempre devolve algo; "não há" é uma decisão de leitura.

O que acontece se o modelo citar um id que não existe?

A validação descarta a citação e conta o motivo (fonte_inexistente). Se sobrar alguma citação válida, a resposta passa com as citações restantes; se não sobrar, é rejeitada e o sistema registra. É o mecanismo do Ex. 6 e da página 7: o modelo pode errar, o código não deixa o erro chegar ao analista.

Validação em código é a última barreira, e é determinística.

Duas chamadas por pergunta é o mínimo?

É. Uma para embutir a pergunta (a lexical não precisa de rede), uma para gerar. Dá para chegar a uma se a pergunta já estiver embutida (cache por hash, capítulo 9) ou se a resposta estiver em cache. Cada etapa "avançada" do capítulo 2 adiciona chamadas, e é por isso que elas precisam se justificar.

Duas é o piso; tudo acima custa e precisa de prova.

Descreva as cinco etapas com o que cada uma recebe, devolve e como se mede. Diga por que o projeto quer o ciclo determinístico.

Capítulo 2

Padrões: do RAG mínimo ao agêntico, e o que o projeto escolheu

O ciclo do capítulo 1 é o RAG mínimo (às vezes chamado de "ingênuo", o que é injusto: com busca híbrida, esquema de saída e validação, ele é a base de sistemas sérios). Sobre ele existem etapas opcionais, cada uma com um ganho específico e um custo em chamadas e latência.

Reescrita da consulta: o modelo transforma a pergunta do usuário numa consulta melhor para a busca (expande siglas, tira ruído, explicita o que se quer). Ganha quando as perguntas chegam mal escritas; custa uma geração. Multi-consulta: gera três ou quatro variações da pergunta, busca com todas e funde (RRF de novo). Ganha recall em perguntas ambíguas; custa uma geração e várias embeddings. HyDE: o modelo escreve uma resposta hipotética e é ela que se embute e busca, porque uma resposta se parece mais com o documento do que a pergunta. Ganha em consultas curtas com vocabulário diferente do corpus; custa uma geração e corre o risco de embutir uma alucinação. Decomposição: quebra perguntas compostas ("o edital atende aos prazos e à garantia?") em subperguntas, cada uma com a sua busca, e sintetiza. Reranker e juiz de aderência (páginas 4 e 7): reordenam e conferem.

O RAG agêntico deixa o modelo decidir, a cada passo, se busca de novo, com qual consulta, e quando parar. É poderoso para perguntas exploratórias e péssimo para auditoria: duas execuções do mesmo documento podem seguir caminhos diferentes, e o custo é imprevisível. GraphRAG e variantes constroem um grafo de entidades e relações sobre o corpus; vale quando as perguntas são sobre relações entre muitas partes ("quais dispositivos foram alterados pela lei X e afetam Y"), não para "o que diz o art. 75". E há a alternativa de não fazer RAG: colocar a lei inteira no contexto de um modelo de janela longa. A página 1 explicou o custo (tokens por chamada, "perdido no meio"); para uma base de dezenas de milhares de dispositivos, não é opção.

O projeto escolheu o mínimo, com busca híbrida forte, esquema, validação e um critério por chamada na auditoria: em vez de decompor perguntas com o modelo, a decomposição já está na lista de critérios, feita por quem sabe. As etapas extras ficam atrás de flags, para entrar quando a avaliação (página 8) mostrar onde o mínimo falha.

Perguntas que aparecem aqui

Como sei se uma etapa extra vale a pena?

Só de um jeito: rodar o conjunto de avaliação com e sem ela e comparar recall, fidelidade e recusa (página 8), com o custo ao lado. Uma etapa que sobe o recall de 0,88 para 0,90 e dobra a latência não vale; uma que sobe de 0,70 para 0,85 vale mesmo cara. Sem medição, é opinião.

A avaliação decide; a intuição só propõe.

Multi-consulta não é só "buscar mais"?

É buscar com formulações diferentes, o que muda o que a busca acha, não só quanto. Ajuda quando a pergunta do usuário está longe do vocabulário do corpus. Mas cada variação é uma embedding e a fusão traz mais candidatos para o reranker filtrar. No projeto, a busca híbrida já cobre parte disso (a lexical acha o vocabulário exato; a vetorial, o sentido), e por isso a multi-consulta ficou de fora do mínimo.

Híbrida resolve parte do que multi-consulta resolveria, sem chamada extra.

O modelo de janela longa não vai tornar o RAG obsoleto?

Para bases pequenas e perguntas ocasionais, colocar tudo no contexto já é razoável. Para uma base grande, com muitas perguntas por dia, custo, latência e "perdido no meio" mantêm o RAG. E há uma razão que não é técnica: a busca produz uma lista curta e citável do que foi usado, que é o que um auditor quer ver. Um contexto de 200 mil tokens não é auditável.

RAG não é só economia; é rastreabilidade.

Capítulo 3

O ciclo de ingestão: da fonte ao índice

Tudo o que o ciclo de consulta faz depende do que a ingestão colocou na base. E a ingestão é onde a sujeira entra: PDFs com cabeçalho em toda página, palavras hifenizadas na quebra de linha, "Este texto não substitui o publicado no DOU", tabelas viradas em texto corrido, notas de rodapé no meio do artigo. Um trecho com esse ruído ganha um vetor deslocado e um tsvector com lexemas inúteis. A ingestão é um pipeline próprio, que roda fora do ciclo de consulta, com sete etapas: fonte (o PDF oficial, ou o HTML do Planalto, com a data de captura), extração (PDF → texto, com a ferramenta certa para o layout; página 9), normalização (limpeza, que o experimento abaixo faz), segmentação (por dispositivo; capítulo 4), enriquecimento (identificador, hierarquia, vigência, hash; capítulos 5 e 6), embedding (em lotes, com tipo de tarefa; página 2) e indexação (inserção idempotente; página 3).

Duas propriedades fazem a ingestão confiável. Idempotência: rodar duas vezes sobre a mesma fonte não duplica nada, porque o identificador é natural e o hash do texto diz se o trecho mudou. Versionamento: cada carga tem uma versão (fonte, data, modelo de embedding), e a consulta sabe contra qual versão rodou. Com as duas, reprocessar é seguro e barato, e é isso que permite melhorar a segmentação ou trocar o modelo sem medo.

Sobre a decisão da base normativa do projeto: curada, não ao vivo. A jurisprudência do TCU é buscada, selecionada e ingerida por um processo controlado, com revisão, e não consultada em tempo real. Ao vivo daria "atualidade" ao custo de conteúdo não revisado entrando no contexto de uma auditoria; curado dá previsibilidade e rastreabilidade, ao custo de uma rotina de atualização. Para conformidade, a segunda vale mais.

Perguntas que aparecem aqui

Limpar demais tem risco?

Tem. Toda regra de limpeza é uma regra que pode apagar conteúdo: um regex de "rodapé" que pega uma linha do texto, uma junção de linhas que cola dois dispositivos. Por isso a limpeza é feita com regras explícitas, testadas em amostras, e o texto bruto é guardado ao lado do limpo (com o hash de cada um): dá para reprocessar quando uma regra melhora.

Guarde o bruto; a limpeza é reprocessável.

Por que a ingestão roda em fila e não no upload?

Porque é lenta (extração, embeddings em lote) e falha por motivos externos (PDF corrompido, cota da API). Numa fila com retentativa e fila de erros (SQS + DLQ no projeto), a falha de um documento não trava o sistema e pode ser reprocessada. O upload só registra o documento e enfileira.

Trabalho lento e falível vai para a fila.

Quando o TCU publica um acórdão novo, como ele entra?

Pela rotina de curadoria: alguém seleciona, o acórdão entra como fonte com data, passa pelo pipeline e recebe versão. Não há busca ao vivo no site do TCU durante uma auditoria. É mais lento e é intencional: o que entra no contexto de uma auditoria passou por revisão.

Curado: previsível e rastreável; ao vivo: atual e sem controle.

Capítulo 4

Segmentação: um dispositivo, um trecho

Segmentar é decidir o que é "um trecho": a unidade que recebe um vetor, um tsvector e um id, e que o modelo lê inteira. A página 2 mostrou o custo de errar para cima (diluição: um trecho com três assuntos fica no meio de todos) e a página 1 o custo de errar para baixo (um inciso sem o caput não diz do que trata). As estratégias genéricas de segmentação existem porque a maioria dos textos não tem estrutura; texto legal tem, e é a melhor notícia desta página.

Tamanho fixo (N caracteres, com sobreposição): simples, cego, corta frases no meio e junta dispositivos. Serve para texto sem estrutura nenhuma. Por frase (agrupa frases até um tamanho): não corta no meio, mas ainda junta o fim de um artigo com o começo do outro. Recursiva (tenta parágrafos, depois frases, depois caracteres): o padrão das bibliotecas, razoável para documentos comuns. Semântica (corta onde o embedding de frases consecutivas muda muito): cara, e para lei é redundante, porque a estrutura já diz onde cortar. Estrutural: um trecho por dispositivo (caput, parágrafo, inciso, alínea), com o caput como prefixo dos incisos e parágrafos. É a do projeto e a do Ex. 2.

Os critérios para julgar uma segmentação estão no experimento: número de trechos, tamanho médio e máximo (o limite de entrada do embedding é 2048 tokens), quantos trechos misturam mais de um dispositivo (diluição) e quantos cortam no meio de uma frase. A estrutural zera os dois últimos por construção. A sobreposição, tão comum nos tutoriais, é um remendo para cortes cegos: quando o corte é estrutural, ela não faz sentido; o contexto que a sobreposição tentaria preservar é o caput, e ele entra como prefixo, não como repetição.

Perguntas que aparecem aqui

E quando um único dispositivo é enorme (um caput de meia página)?

Fica como um trecho enquanto couber no limite do embedding (2048 tokens no embedding-001); acima disso, corta por frase dentro do dispositivo, mantendo o mesmo id com um sufixo de parte (-p1, -p2) e o cabeçalho repetido. É raro em lei; é comum em acórdãos, e é a regra do projeto para eles.

Estrutura primeiro; tamanho só quando a estrutura estoura o limite.

O caput como prefixo não duplica texto no índice?

Duplica um pouco (as primeiras palavras do caput em cada inciso), e vale: o inciso "I – para obras e serviços de engenharia" sozinho não diz que é sobre dispensa de licitação. O prefixo torna cada trecho legível isolado, para o vetor e para o modelo. O custo em tokens é pequeno porque o prefixo é curto (o guia corta em 80 caracteres).

Legibilidade isolada vale mais que economia de tokens.

Como segmentar um edital, que não tem "art."?

Editais têm estrutura própria (itens numerados 1, 1.1, 1.1.1; anexos; cláusulas do contrato). A mesma ideia vale: um trecho por item, com o item pai como prefixo, e um id natural (EDITAL-2024-12-item-7.3). O que muda é o regex; o princípio, não. A página 9 trata da extração e dos regex.

Todo documento normativo tem hierarquia; ache a dele.

Capítulo 5

Identificadores naturais e metadados

Cada trecho precisa de um nome que não mude. Se o id fosse um número sequencial ou um UUID gerado na carga, reindexar a base daria ids novos e toda citação antiga ("a resposta X citou o trecho 4821") ficaria órfã. O projeto usa identificadores naturais: derivados do conteúdo, L14133-art75-incI, L14133-art75-p3, DEC10024-art3-incII-b. O mesmo dispositivo produz o mesmo id em qualquer carga; um id que aparece numa citação pode ser resolvido para o texto anos depois; e o analista lê o id e sabe do que se trata.

A convenção: norma (sigla e número sem pontuação), artigo, e a subdivisão na ordem da hierarquia: parágrafo (p2, pu para parágrafo único), inciso (incIII, em romano como na lei), alínea (b). Caput explícito quando o artigo tem subdivisões (-caput), para não confundir o artigo inteiro com a cabeça dele. Tudo derivado por um parser de referências, o mesmo que depois interpreta citações escritas pelo modelo ("art. 75, § 2º, III") e as converte em ids para validar.

Ao lado do id, os metadados que a consulta filtra e o analista vê: norma, artigo, hierarquia (caput / parágrafo / inciso / alínea), tema (opcional, atribuído na curadoria), vigencia_inicio e vigencia_fim (capítulo 6), hash_texto (para saber se mudou), fonte e versao_carga. Nada disso vai para o embedding; vai para colunas, onde o SQL filtra de graça.

Perguntas que aparecem aqui

E se dois dispositivos tiverem o mesmo id (uma lei alterada que renumera)?

O id natural identifica o dispositivo, não a redação: o art. 75, I, continua sendo art. 75, I, mesmo com o valor atualizado. Quem distingue redações é a vigência (capítulo 6): duas linhas com o mesmo id lógico e vigências diferentes, e a chave primária vira (id, vigencia_inicio). Renumeração de verdade (um artigo vira outro) é raríssima e se trata como dispositivo novo com nota de equivalência.

Id = dispositivo; vigência = redação; juntos, a chave.

Por que não usar o hash do texto como id?

Porque o hash muda quando o texto muda (é para isso que ele existe) e ninguém lê um hash. Hash é para detectar mudança e evitar reembutir; id é para citar e resolver. Duas funções, duas colunas.

Hash detecta mudança; id nomeia.

Os metadados deveriam entrar no texto embutido?

O que ajuda o vetor a entender o trecho, sim: o cabeçalho do dispositivo ("Art. 75, I") e o caput como prefixo. O que serve para filtrar (vigência, norma, tema), não: vai para colunas. Embutir "vigente desde 2021" no texto não faz o vetor filtrar por data; só adiciona ruído.

No texto o que dá sentido; na coluna o que filtra.

Capítulo 6

Vigência: a norma certa para a data do documento

Uma auditoria de conformidade pergunta "este edital, publicado nesta data, cumpre a norma que valia nesta data?". A Lei 14.133 mudou desde 2021 (dispositivos alterados, valores do art. 75 atualizados anualmente por decreto, prazos de transição), e uma base que só guarda a redação atual responde errado sobre qualquer documento antigo, com toda a confiança. A solução é tratar a redação como versão com vigência: cada trecho tem vigencia_inicio e vigencia_fim (nula se ainda vigente), o mesmo id lógico pode ter várias linhas, e a consulta filtra pela data do documento analisado.

Na prática, três regras. A busca sempre recebe uma data (a do documento; hoje, para perguntas livres) e aplica o filtro nas duas CTEs da híbrida (página 4). A ingestão de uma alteração fecha a vigência da linha antiga e abre uma nova, nunca sobrescreve. E a resposta ao analista mostra a vigência do trecho citado ("art. 75, I, redação vigente de 1/1/2024 a 31/12/2024"), porque um auditor vai perguntar. O filtro de vigência é também o caso de uso principal da varredura iterativa da página 3: para documentos antigos, ele fica seletivo.

Perguntas que aparecem aqui

De onde vêm as datas de vigência?

Da própria norma alteradora ("esta lei entra em vigor em…", "produz efeitos a partir de…") e dos decretos de atualização de valores. A curadoria registra a data ao ingerir a alteração; é trabalho humano assistido, e é a parte da ingestão que mais exige revisão, porque um erro de data é um erro de auditoria.

Vigência é dado curado, não extraído automaticamente.

E a redação "dada por" outra lei: como o trecho mostra isso?

Com uma coluna alterado_por (id da norma alteradora) e o texto da redação nova como uma linha nova. O trecho antigo continua na base, com vigência fechada, e continua sendo encontrado para documentos do período dele. Nada é apagado; tudo é datado.

Apagar destrói a auditoria de documentos antigos.

O embedding muda entre versões do mesmo dispositivo?

Se o texto mudou, sim (hash diferente, reembute). Se só a vigência mudou (o texto é o mesmo e a data de fim foi preenchida), não: o hash é igual e o vetor é reaproveitado. É a idempotência do capítulo 3 funcionando.

Reembute o texto que mudou; a vigência é só coluna.

Escreva as três regras de vigência do projeto e o que acontece com uma auditoria de documento antigo se a base só tiver a redação atual.

Capítulo 7

Montar o prompt: orçamento, ordem e delimitação

Entre a busca e o modelo há uma etapa que parece trivial e decide muito: transformar 12 trechos e uma pergunta em um prompt. Três decisões. Orçamento: quantos tokens o contexto pode ter, dado o modelo, o custo e o tamanho da resposta. Com trechos de dispositivo (100 a 300 tokens cada), 12 trechos são 2 a 4 mil tokens: barato, e longe do ponto em que o modelo começa a perder o meio. Ordem: a página 1 mostrou que o começo e o fim do contexto são mais bem usados; com 12 trechos o efeito é pequeno, e o projeto mantém a ordem da fusão (mais relevante primeiro); com 30 ou mais, vale colocar os melhores nas pontas. Delimitação: cada trecho vai entre tags com o id e o dispositivo, o bloco todo entre <contexto>, e a instrução de sistema diz que aquilo é dado, não instrução. É o que permite citar por id e é a primeira defesa contra um documento que tente dar ordens ao modelo (página 7).

A pergunta vai no fim, depois do contexto: é o que o modelo precisa "ter em mente" ao gerar. A instrução de sistema é fixa e curta, e diz quatro coisas: use só o contexto; cite ids; se não houver evidência, diga; formato de saída. Tudo o que varia (trechos, pergunta, critério) fica no prompt de usuário. Essa separação é o que faz o cache de prefixo funcionar e o que a página 6 chama de "versionar o prompt".

Perguntas que aparecem aqui

Por que tags XML e não JSON ou markdown para os trechos?

Porque tags com atributos (<trecho id="…" dispositivo="…">) são legíveis pelo modelo, difíceis de confundir com o conteúdo, e permitem colocar o id onde o modelo o vê ao ler o texto. JSON obriga a escapar aspas e quebras; markdown não tem delimitador forte. Os modelos do Google e da Anthropic foram treinados com muito texto assim delimitado.

Delimitador visível, com metadado, sem escape.

Devo incluir o score da busca no contexto?

Não. O modelo não sabe usar "cosseno 0,71" e pode tratar o número como parte do conteúdo. A ordem já carrega a informação de relevância. O score fica no log.

Ordem sim, número não.

Instrução de sistema longa ou curta?

Curta e precisa. Cada regra a mais é uma que o modelo pode ignorar ou aplicar demais. Quatro ou cinco frases cobrem "só o contexto, cite, recuse, formato". Regras específicas de uma tarefa (o critério de auditoria) vão no prompt de usuário, junto com o que elas se aplicam.

Sistema: regras gerais; usuário: a tarefa concreta.

Escreva as três decisões de montagem do prompt com a escolha do projeto em cada uma, e as quatro frases da instrução de sistema com as suas palavras.

Perguntas que aparecem aqui

O que é o id de correlação?

Um identificador único por execução (por pergunta, ou por critério de auditoria), gravado em toda linha de log das etapas daquela execução. Com ele, um sintoma vira uma busca: "me dê tudo o que aconteceu na execução X", da busca à validação. Sem ele, os logs das etapas são quatro arquivos que não se conversam.

Um id, quatro etapas, uma história.

Registrar o prompt inteiro em log não é caro?

Registre a versão do prompt e os ids dos trechos, não o texto: com isso o prompt é reconstruível. O texto da resposta, sim, registre (é pequeno e é o que o analista vê). Para investigação profunda, uma amostra das execuções com o prompt completo basta.

Reconstruível vale mais que armazenado.

Como pegar a degradação silenciosa do modelo?

Rodando o conjunto de avaliação em rotina (diária ou a cada deploy) e comparando com o número anterior. Provedores atualizam modelos com o mesmo nome; a única defesa é medir sempre. A página 8 monta a rotina.

O que não se mede em rotina degrada em silêncio.

Capítulo 9

Cache, idempotência e a conta do volume

O RAG tem três lugares onde o mesmo trabalho se repete, e cada um tem um cache com uma chave própria. Embedding por hash do texto: o mesmo trecho (mesmo hash, mesmo modelo) nunca é embutido duas vezes; na reingestão, só o que mudou custa. Resposta por (hash da pergunta normalizada, versão da base, versão do prompt): a mesma pergunta sobre a mesma base tem a mesma resposta, e para os critérios de auditoria, que se repetem em todo documento, isso é frequente. Prefixo do prompt no provedor: a instrução de sistema, e o contexto quando repete, podem ser cobrados mais barato pelo cache implícito do Gemini (página 1); a separação fixo/variável do capítulo 7 é o que torna isso possível.

Idempotência é o cache visto da ingestão: rodar de novo produz o mesmo estado, sem duplicar e sem reembutir o que não mudou. A chave é o id natural; o detector de mudança é o hash. Junte a isso a fila com retentativa (uma mensagem processada duas vezes não pode criar dois trechos) e a ingestão fica segura para falhar no meio e recomeçar.

A conta do volume é o que dimensiona cota e custo. Ingestão: documentos por dia × trechos por documento × tokens por trecho, em lotes de 16. Consulta: perguntas por dia × (instrução + k trechos + pergunta) tokens de entrada e algumas centenas de saída, uma chamada de geração e uma de embedding por pergunta. Para a auditoria, "pergunta" é critério: 40 critérios por documento são 40 gerações. A calculadora faz a conta e mostra quanto o cache de resposta economiza.

Perguntas que aparecem aqui

Cache de resposta não corre o risco de responder com base desatualizada?

Não se a versão da base fizer parte da chave: quando a base muda, a chave muda e o cache não acerta. É por isso que versão de base e versão de prompt entram na chave, e é o motivo de nunca "atualizar no lugar" a base.

Versão na chave: cache que nunca mente.

Como normalizar a pergunta para o hash do cache?

Minúsculas, espaços colapsados, acentos removidos, pontuação final removida. Não mais que isso: "prazo de pagamento" e "prazo para pagar" são perguntas diferentes para o cache (e o embedding as aproxima na busca, não no cache). Para os critérios de auditoria, o texto é fixo e o hash é estável por construção.

Normalize a superfície; não tente normalizar o sentido.

A fila pode entregar a mesma mensagem duas vezes?

Pode (SQS padrão garante "pelo menos uma vez"). Idempotência no consumidor é obrigatória: inserir por id com ON CONFLICT DO UPDATE condicionado ao hash, e registrar a mensagem processada. É o que torna a retentativa segura.

Entrega duplicada é normal; efeito duplicado é bug.

Escreva as três chaves de cache do sistema e por que a versão da base entra em uma delas; depois, a conta de chamadas por documento auditado.

Capítulo 10

No projeto, checklist e autoavaliação

No projeto

O ia-worker (FastAPI) tem os dois ciclos como dois módulos. Ingestão: consome a fila SQS; para cada mensagem (documento ou norma), baixa o arquivo do S3, extrai, normaliza, segmenta por dispositivo, enriquece (id natural, hierarquia, vigência, hash), embute em lotes de 16 com RETRIEVAL_DOCUMENT e grava em rag.trecho_normativo com ON CONFLICT (id, vigencia_inicio) DO UPDATE condicionado ao hash; registra a versão da carga; em falha, a mensagem volta para a fila e, após as retentativas, para a DLQ. Consulta: recebe pergunta ou critério mais a data do documento; embute a consulta com RETRIEVAL_QUERY; roda a híbrida com filtro de vigência; monta o prompt (sistema fixo versionado + contexto delimitado + pergunta); chama o Gemini com esquema; valida em código; grava o rastro com id de correlação; devolve resposta, citações válidas e a versão de tudo. Cache de resposta por (hash da pergunta, versão da base, versão do prompt); cache de embedding por hash do texto. A base normativa é curada: fontes selecionadas, ingeridas por lote, versionadas.

O Ex. 2 (VIN-6) é a metade da ingestão que dá para fazer sem banco: PDF da Lei 14.133 → texto limpo → trechos por dispositivo em JSONL, com id natural, hierarquia e hash. O Ex. 3 os coloca no pgvector; o Ex. 5 monta o prompt; o Ex. 6 valida.

# ingestao/segmentar.py — texto limpo → trechos por dispositivo (Ex. 2)
import re, json, hashlib
from dataclasses import dataclass, asdict

RE_ART = re.compile(r"^Art\.\s*(\d+)[º°]?\.?\s*(.*)$")
RE_PAR = re.compile(r"^§\s*(\d+)[º°]?\s*(.*)$|^Parágrafo único\.?\s*(.*)$")
RE_INC = re.compile(r"^([IVXL]+)\s*[-–]\s*(.*)$")
RE_ALI = re.compile(r"^([a-z])\)\s*(.*)$")

@dataclass
class Trecho:
    id: str; norma: str; artigo: int; hierarquia: str; dispositivo: str; conteudo: str; hash_texto: str
    vigencia_inicio: str = "2021-04-01"; vigencia_fim: str | None = None

def h(t: str) -> str: return hashlib.sha256(t.strip().encode()).hexdigest()[:16]

def segmentar(texto: str, norma: str = "L14133") -> list[Trecho]:
    out, art, caput, par, inc = [], None, "", None, None
    for linha in texto.splitlines():
        l = linha.strip()
        if not l: continue
        if m := RE_ART.match(l):
            art, caput, par, inc = int(m[1]), m[2], None, None
            out.append(Trecho(f"{norma}-art{art}-caput", norma, art, "caput", f"Art. {art}, caput", caput, h(caput)))
        elif art and (m := RE_PAR.match(l)):
            par, inc = (m[1] or "unico"), None; txt = m[2] or m[3]
            pid = "pu" if par == "unico" else f"p{par}"
            out.append(Trecho(f"{norma}-art{art}-{pid}", norma, art, "paragrafo", f"Art. {art}, § {par}", f"{caput[:80]}… {txt}", h(txt)))
        elif art and (m := RE_INC.match(l)):
            inc = m[1]; base = f"-p{par}" if par and par != "unico" else ("-pu" if par else "")
            out.append(Trecho(f"{norma}-art{art}{base}-inc{inc}", norma, art, "inciso", f"Art. {art}, {inc}", f"{caput[:80]}… {inc} – {m[2]}", h(m[2])))
        elif art and inc and (m := RE_ALI.match(l)):
            out.append(Trecho(f"{norma}-art{art}-inc{inc}-{m[1]}", norma, art, "alinea", f"Art. {art}, {inc}, {m[1]}", f"{caput[:80]}… {inc}, {m[1]}) {m[2]}", h(m[2])))
        elif out:
            out[-1].conteudo += " " + l; out[-1].hash_texto = h(out[-1].conteudo)   # continuação de linha
    return out

def salvar_jsonl(trechos: list[Trecho], caminho: str) -> None:
    with open(caminho, "w", encoding="utf-8") as f:
        for t in trechos: f.write(json.dumps(asdict(t), ensure_ascii=False) + "\n")
# ingestao/indexar.py — JSONL → pgvector, idempotente por (id, vigencia_inicio) e hash (Ex. 3)
import json, psycopg
from embutir import embutir, MODELO, DIMS

UPSERT = """
INSERT INTO rag.trecho_normativo (id, norma, artigo, hierarquia, dispositivo, conteudo, hash_texto,
        vigencia_inicio, vigencia_fim, embedding, modelo_embedding, dimensoes, versao_carga)
VALUES (%(id)s, %(norma)s, %(artigo)s, %(hierarquia)s, %(dispositivo)s, %(conteudo)s, %(hash_texto)s,
        %(vigencia_inicio)s, %(vigencia_fim)s, %(embedding)s::vector, %(modelo)s, %(dims)s, %(versao)s)
ON CONFLICT (id, vigencia_inicio) DO UPDATE SET
  conteudo = EXCLUDED.conteudo, hash_texto = EXCLUDED.hash_texto, embedding = EXCLUDED.embedding,
  modelo_embedding = EXCLUDED.modelo_embedding, versao_carga = EXCLUDED.versao_carga
WHERE rag.trecho_normativo.hash_texto IS DISTINCT FROM EXCLUDED.hash_texto      -- só reescreve o que mudou
   OR rag.trecho_normativo.modelo_embedding IS DISTINCT FROM EXCLUDED.modelo_embedding
"""

def indexar(caminho_jsonl: str, versao: str) -> None:
    trechos = [json.loads(l) for l in open(caminho_jsonl, encoding="utf-8")]
    with psycopg.connect() as conn:
        # quais precisam de embedding novo? (hash ou modelo diferentes do que está no banco)
        atuais = dict(conn.execute("SELECT id || '|' || vigencia_inicio, hash_texto FROM rag.trecho_normativo WHERE modelo_embedding = %s", (MODELO,)).fetchall())
        novos = [t for t in trechos if atuais.get(f"{t['id']}|{t['vigencia_inicio']}") != t["hash_texto"]]
        vetores = embutir([f"{t['dispositivo']}. {t['conteudo']}" for t in novos], "RETRIEVAL_DOCUMENT")   # lotes de 16
        for t, v in zip(novos, vetores):
            conn.execute(UPSERT, {**t, "embedding": str(v), "modelo": MODELO, "dims": DIMS, "versao": versao})
        conn.commit()
    print(f"{len(novos)} de {len(trechos)} trechos (re)embutidos; versão {versao}")
# consulta/rag.py — o ciclo de consulta do ia-worker, resumido (Ex. 5 e 6 detalham prompt e validação)
import uuid, time, json
from busca import hibrida            # página 4: 50 + 50 candidatos, RRF K = 60, filtro de vigência
from prompt import montar, SISTEMA_V3   # página 6: sistema fixo versionado + contexto delimitado + pergunta
from validar import validar         # página 7: citações existem? estão no contexto? esquema ok?

def responder(pergunta: str, data_documento: str, k: int = 12) -> dict:
    cid, t0 = str(uuid.uuid4()), time.perf_counter(); rastro = {"cid": cid}
    trechos = hibrida(pergunta, data_documento, k=k); rastro["busca_ms"] = (time.perf_counter() - t0) * 1000
    rastro["ids"] = [t["id"] for t in trechos]
    prompt = montar(SISTEMA_V3, trechos, pergunta)
    t1 = time.perf_counter(); bruto = gerar(prompt); rastro["geracao_ms"] = (time.perf_counter() - t1) * 1000
    resultado = validar(json.loads(bruto), contexto_ids=rastro["ids"])
    rastro.update(resultado["motivos"], ok=resultado["ok"], versao_prompt="v3", versao_base=versao_base_atual())
    registrar(rastro)                # uma linha por execução, com o id de correlação
    return {"cid": cid, **resultado, "trechos": trechos}
